Every interaction with a Kubernetes cluster—whether it originates from a command-line tool like kubectl, an internal controller, or an external operator—must pass through the kube-apiserver’s request pipeline. Understanding these stages is essential for building secure, efficient, and extension-ready Kubernetes applications.

When a request enters the kube-apiserver, it doesn't immediately interact with etcd. Instead, it moves through a chain of stages, each handling a specific concern. For a mutation, these stages occur in a precise order.

First is Authentication, which validates the caller's identity using X.509 client certificates, bearer tokens, or OIDC tokens. If this fails, the request is rejected with a 401 Unauthorized response.

Second, the Audit stage records the request for compliance and debugging, ensuring there is a full trail of activity.

Third is Impersonation, which allows authenticated users to act as another user or group, provided they have the necessary permissions.

Fourth is Priority and Fairness. This stage classifies requests into flow schemas and priority levels to prevent the API server from becoming overloaded. It categorizes requests—such as distinguishing between leader election and background listing—to ensure cluster stability. Keep in mind that this is how the API server prevents a misbehaving controller from starving other clients. Without this, a single controller could issue a flood of calls and degrade responsiveness for the entire cluster.

Fifth is Authorization, where the system checks if the authenticated identity is permitted to perform the requested action on the specified resource. Kubernetes supports several modes here, including RBAC, Node, Webhook, and ABAC.

Sixth is the Mutation stage. During this phase, mutating admission webhooks can modify the request object before it is validated. This is where you might see sidecars injected, default values set by policy engines, or labels added automatically.

Seventh is Validation. Schema validation and validating admission webhooks ensure the object meets all constraints. Unlike the mutation stage, these webhooks cannot change the object; they can only accept or reject it.

Finally, the Storage stage occurs, where the validated object is serialized and persisted to etcd. At this point, the desired state is durably recorded and ready for controllers to act on.

As you work with these systems, please note that a vulnerability in HTTP/2, known as the "rapid reset" attack, led the client-go library to fall back to HTTP/1.1 connections by default. This is an important detail to keep in mind when debugging connection behavior between your clients and the API server.

Now, let's look at how to explore the API. The kube-apiserver exposes discovery endpoints that allow you to inspect available API groups, versions, and resource types. This is a great way to verify that your requests are reaching the server and to understand the shape of the API surface.

To explore this, you can start a local proxy to the API server by running the command: `kubectl proxy --port=8001`.

Once the proxy is running, you can list all API groups by using a curl command against the localhost address at port 8001, targeting the /apis endpoint. You can also fetch the aggregated discovery document in version 2 format by adding the appropriate Accept header to your request. Finally, you can inspect a specific resource, such as the pods in the default namespace, by querying the /api/v1/namespaces/default/pods endpoint.

These commands confirm that your request is successfully passing through the authentication and authorization stages. Furthermore, these discovery endpoints are exactly what client libraries, like client-go, use under the hood to negotiate API versions and resource schemas.
