#  CRUD operations and apply/patch/update semantics

= CRUD Operations and Apply/Patch/Update Semantics

In the Kubernetes control plane, the way we modify state is critical. Because Kubernetes is an eventually consistent, distributed system, simple CRUD (Create, Read, Update, Delete) operations have evolved into more sophisticated patterns to handle concurrent updates and maintain system integrity.

== Understanding API Semantics

When interacting with the `kube-apiserver`, you have three primary methods for modifying existing resources. Choosing the right one is essential for building robust controllers.

=== 1. Update (The "Put" Equivalent)
An **Update** operation is a full-object replacement.
*   **Mechanism:** The client sends the entire object definition to the API server.
*   **Concurrency:** It requires the `metadata.resourceVersion` to match the current version in `etcd`. If the version has changed (due to another controller acting on the object), the API server returns a `409 Conflict` error.
*   **Use Case:** Best used when you have the complete state and want to ensure you are modifying the specific version you read.

=== 2. Patch (Partial Updates)
A **Patch** modifies only specific fields without requiring the full object body. Kubernetes supports several types of patching:

*   **Strategic Merge Patch:** The default for built-in Kubernetes resources. It understands the schema of resources (e.g., how to merge items in a list).
*   **JSON Patch (RFC 6902):** A sequence of operations (add, remove, replace, move, test).
*   **Merge Patch (RFC 7386):** A simple JSON merge where `null` values explicitly delete fields.

[TIP]
====
When using Strategic Merge Patch, you can use the **`$retainKeys`** directive to explicitly drop fields from a list or map, providing granular control over object state that standard merging might otherwise preserve.
====

=== 3. Server-Side Apply (SSA)
Server-Side Apply is the modern standard for declarative configuration management. It shifts the logic of merging from the client to the `kube-apiserver`.

*   **Ownership:** SSA tracks "Field Managers." If two controllers attempt to modify the same field, the API server detects a conflict.
*   **Efficiency:** It eliminates the "get-modify-put" race condition cycle that plagues traditional clients.
*   **Observability:** Each field maintains metadata about which manager last updated it, making debugging complex reconciliation loops much easier.

== Comparison Summary

[cols="1,1,1", options="header"]
|===
| Feature | Update | Patch | Server-Side Apply
| **Payload Size** | Full Object | Partial | Partial/Declarative
| **Conflict Handling** | Optimistic Locking | Depends on Patch type | Field Manager tracking
| **Logic Location** | Client | Client | Server
|===

== Hands-on Activity: Observing Patch Semantics

In this exercise, you will observe how a `Patch` behaves compared to a full `Update`.

=== Prerequisites
*   A running Kubernetes cluster (or `kind`).
*   `kubectl` configured.

=== Step 1: Create a Resource
Create a simple ConfigMap to experiment with:

[source,bash]
----
kubectl create configmap demo-config --from-literal=key1=value1
----

=== Step 2: Perform a Strategic Merge Patch
Add a second key to the ConfigMap without including `key1` in your request:

[source,bash]
----
kubectl patch configmap demo-config -p '{"data": {"key2": "value2"}}'
----

Verify the result:
[source,bash]
----
kubectl get configmap demo-config -o yaml
----
*Observation: `key1` is preserved because the Patch operation only modified the specific keys provided.*

=== Step 3: Trigger a Conflict (Simulated)
To understand why we prefer Patches/SSA over Updates in controllers:
1. Open two terminals.
2. In Terminal A, get the object: `kubectl get cm demo-config -o yaml > obj.yaml`.
3. In Terminal B, edit `obj.yaml` and change a field, then run `kubectl apply -f obj.yaml`.
4. Now, modify `obj.yaml` in Terminal A and run `kubectl apply -f obj.yaml`. 
*Result: You will trigger a conflict error because the `resourceVersion` has advanced.*

=== Troubleshooting Guidance
*   **Conflict Errors:** If your controller receives a `409 Conflict`, you should implement a retry strategy: re-fetch the object, re-apply your logic, and try the Update again.
*   **`observedGeneration`:** Always ensure your controller checks `.status.conditions[].observedGeneration` against the object's `.metadata.generation` to ensure you are acting on the latest intent, not stale cached data.
