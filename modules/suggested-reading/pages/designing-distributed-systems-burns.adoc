#  Designing Distributed Systems (Burns)

= Designing Distributed Systems: A Kubernetes Developer's Perspective

Drawing from Brendan Burns' foundational work, *Designing Distributed Systems*, we explore the patterns required to manage the inherent complexity of Kubernetes-based environments. As a Kubernetes developer, understanding these patterns is the difference between building a fragile script and engineering a robust, self-healing system.

== The Core Philosophy: Patterns over Components

In a distributed system like Kubernetes, you cannot rely on synchronous communication. Instead, you must design for **eventual consistency** and **decoupled execution**. Burns emphasizes that by combining primitive building blocks—such as the Sidecar, Ambassador, and Work Queue—we can achieve the same complexity as traditional monolithic systems, but with the added benefits of horizontal scalability and resilience.

=== Key Architectural Patterns
*   **The Sidecar Pattern:** Attaching a secondary container to a primary application container to extend its functionality (e.g., logging, monitoring, or service mesh proxies) without modifying the application code.
*   **The Ambassador Pattern:** A proxy container that hides the complexity of external service connections, allowing the application to communicate with a local endpoint.
*   **The Adapter Pattern:** Standardizing the output of an application so that it can be consumed by monitoring or logging systems, regardless of the application's internal format.
*   **The Work Queue System:** Utilizing `client-go` informers and work queues to manage tasks asynchronously, ensuring that your controller doesn't block while waiting for API server responses.

== Practical Application: Implementing a Sidecar Pattern

In this exercise, we will implement a simple Sidecar pattern. We will use a primary Nginx container and a "Log-Router" sidecar that reads the Nginx access logs and forwards them to a standard output, simulating a logging agent.

=== Hands-on Activity: Deploying a Sidecar

1.  **Define the Pod Specification**
    Create a file named `sidecar-pod.yaml`:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: nginx-with-sidecar
spec:
  containers:
  - name: nginx
    image: nginx
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/nginx
  - name: log-router
    image: busybox
    command: ["/bin/sh"]
    args: ["-c", "tail -f /var/log/nginx/access.log"]
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/nginx
  volumes:
  - name: log-storage
    emptyDir: {}
----

2.  **Deploy and Verify**
    Apply the manifest and inspect the shared volume:

[source,bash]
----
kubectl apply -f sidecar-pod.yaml
# Observe the sidecar reading logs from the shared volume
kubectl logs nginx-with-sidecar -c log-router
----

== Designing for Failure: Locks and Leases

When applying these distributed patterns to your own custom controllers, you will encounter the **"Split Brain"** scenario. If you run multiple instances of a controller for high availability, they may attempt to reconcile the same resource simultaneously, leading to race conditions.

To prevent this, we move from simple loops to **Leader Election** using Kubernetes `Leases`.

[TIP]
====
Refer to the `coordination.k8s.io` API group. By using the `Lease` object, your controllers can participate in a leader election process. Only the current leader reconciles the state, while others standby, ensuring that your distributed system maintains atomicity and consistency.
====

== Further Exploration
To master these concepts, align your development strategy with these principles:
*   **Idempotency:** Every reconcile action must be safe to repeat, even if the previous attempt failed halfway.
*   **Observability:** If a system is distributed, it must expose metrics via the Adapter pattern to prove it is working as intended.
*   **Eventual Consistency:** Never assume the API server state matches the cluster state instantaneously; always rely on the Informer cache.
