#  Controller sharding strategies

= Controller Sharding Strategies

In large-scale Kubernetes environments, a single controller instance can become a bottleneck. As the number of managed resources grows into the thousands or tens of thousands, the processing latency of the reconciliation loop increases, and the memory footprint may exceed reasonable limits. **Controller sharding** is the architectural pattern used to partition the workload across multiple controller instances, ensuring horizontal scalability and high availability.

== The Need for Sharding

When a controller manages a large set of objects (e.g., thousands of `Ingress` resources), several issues arise:

*   **Reconciliation Latency:** The time taken to process the queue increases as more events flood the system.
*   **API Server Pressure:** Every controller instance maintains its own set of informers. High-frequency listing and watching can overwhelm the `kube-apiserver`.
*   **Blast Radius:** If a single controller instance crashes or enters a "crash loop," the entire system state for all managed resources becomes stale.

Sharding allows us to distribute the "responsibility" for specific subsets of resources, effectively partitioning the workload.

== Architectural Approaches to Sharding

There are two primary strategies for sharding controllers in Kubernetes:

=== 1. Static Sharding
In this model, the workload is partitioned based on a property of the object, such as a hash of the object's name or a label. 

*   **Mechanism:** Each controller instance is assigned a unique ID. When an event arrives, the controller calculates `hash(resource_name) % total_shards`. If the result matches its assigned ID, the controller processes the object; otherwise, it ignores it.
*   **Pros:** Simple to implement; no coordination required between instances.
*   **Cons:** Resharding (changing the number of instances) causes a re-calculation of all assignments, which can trigger massive reconciliation churn.

=== 2. Dynamic Sharding (Lease-based)
Dynamic sharding uses the `Lease` API (from the `coordination.k8s.io` group) to coordinate ownership of shards.

*   **Mechanism:** Controllers compete for "shard leases." Once a controller acquires a lease for a specific shard, it becomes the exclusive owner of that segment of the workload.
*   **Pros:** Highly resilient; if a controller dies, another instance can acquire the expired lease, ensuring automatic failover.
*   **Cons:** Requires managing the coordination layer (etcd/API server) and handling potential race conditions during lease handover.

== Case Study: OpenShift Ingress Controller
The OpenShift `ingress-controller` provides a practical example of sharding. To manage high-traffic clusters, OpenShift allows operators to shard routes across multiple Ingress Controller deployments.

*   **Label-based selection:** You can configure an Ingress Controller to only claim `Routes` that match a specific label (e.g., `ingress-shard: public`).
*   **Availability:** By using overlapping shards, administrators can ensure that if one shard is overwhelmed or unreachable, traffic might still be routed or processed via secondary shards, depending on the load balancer configuration.

== Hands-on Activity: Planning a Sharded Controller

In this exercise, you will design the sharding logic for a hypothetical "CustomConfig" controller.

. **Define the Shard Key:**
   Determine the partitioning criteria. For our example, we will use a label on the resource: `sharding.example.com/id`.

. **Implement Filter Logic:**
   In your controller's `EventHandler`, ensure you verify ownership before adding the item to the workqueue:
+
[source,go]
----
func (c *Controller) shouldProcess(obj interface{}) bool {
    metaObj := obj.(metav1.Object)
    shardID := metaObj.GetLabels()["sharding.example.com/id"]
    
    // Check if this shardID belongs to this instance
    return shardID == c.myShardID
}
----

. **Reflect on Reconciliation:**
   Consider what happens if a resource is created *without* the label. 
   *   *Challenge:* Should it be ignored? Assigned to a "default" shard? 
   *   *Best Practice:* Always define a fallback or "default" behavior for unassigned resources to avoid orphaned objects.

== Summary for Distributed Controllers
*   **Use Leader Election** (via `client-go/tools/leaderelection`) when you have a singleton controller to ensure high availability.
*   **Use Sharding** when the volume of resources exceeds the processing capacity of a single controller.
*   **Always aim for idempotency.** Because network partitions or timing issues might cause two controllers to briefly think they own a resource, your `Reconcile` function must handle concurrent updates gracefully using optimistic locking.
