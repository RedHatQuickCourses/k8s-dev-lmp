#  Designing idempotent state machines

= Designing Idempotent State Machines

In the Kubernetes control plane, the core philosophy is **level-triggered reconciliation** rather than edge-triggered events. Because the network is unreliable and components may restart, your controllers must be designed as **idempotent state machines**.

An operation is idempotent if performing it multiple times results in the same state as performing it once. In Kubernetes, this means your `Reconcile` function must be able to handle being called repeatedly—even if the previous execution failed halfway through—without causing side effects or duplicate actions.

== The Core Principles

To design idempotent systems, follow these three pillars:

1. **Observe before Act:** Never assume the current state. Always query the API server (or cache) to determine if an action is actually necessary.
2. **Deterministic Outputs:** Ensure that given the same input, your logic produces the same outcome. Avoid randomness or non-deterministic time-based calculations inside the reconciliation loop.
3. **Atomic State Transitions:** Utilize Kubernetes primitives like `Status` conditions and `ResourceVersions` to ensure you are only acting upon the latest version of the truth.

== Anatomy of an Idempotent Reconcile Loop

When writing a controller, the structure of your logic should follow this pattern:

[source,go]
----
func (r *MyReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // 1. Fetch the latest instance
    obj := &v1alpha1.MyCustomResource{}
    if err := r.Get(ctx, req.NamespacedName, obj); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 2. Determine "what needs to happen" (Diffing)
    // Avoid blindly creating resources. Check if they exist first.
    if !isStateDesired(obj) {
        // 3. Perform atomic update
        err := r.applyChanges(ctx, obj)
        if err != nil {
            return ctrl.Result{}, err // Requeue on failure
        }
    }

    // 4. Update Status (Idempotent update of observed state)
    return ctrl.Result{}, r.updateStatus(ctx, obj)
}
----

== Handling Conflicts: Optimistic Concurrency

Kubernetes uses **Optimistic Concurrency Control (OCC)**. Every resource has a `metadata.resourceVersion`. If you attempt to update a resource that has changed since you last read it, the API server will reject your request with a `409 Conflict` error.

* **The Idempotent Response:** Do not treat a conflict as a fatal error. Instead, treat it as a trigger to re-read the latest state and reconcile again. The controller-runtime library handles this automatically when you use `client.Update` or `client.Patch`.

== Hands-on Activity: Designing for Idempotency

In this exercise, you will modify a reconciliation loop to move from "imperative" logic (which causes side effects) to "idempotent" logic.

=== Scenario
You are writing a controller that ensures a ConfigMap exists for every `App` resource.

**Imperative (Wrong):**
[source,go]
----
// This fails if the ConfigMap already exists!
err := r.Create(ctx, myConfigMap)
if err != nil {
    return err 
}
----

**Idempotent (Correct):**
[source,go]
----
// 1. Attempt to find the object
found := &corev1.ConfigMap{}
err := r.Get(ctx, types.NamespacedName{Name: name, Namespace: ns}, found)

if errors.IsNotFound(err) {
    // 2. Only create if it does not exist
    return r.Create(ctx, myConfigMap)
} else if err != nil {
    return err
}

// 3. If it exists, verify it matches desired state. 
// If not, perform an Update or Patch.
if !reflect.DeepEqual(found.Data, desiredData) {
    found.Data = desiredData
    return r.Update(ctx, found)
}
----
