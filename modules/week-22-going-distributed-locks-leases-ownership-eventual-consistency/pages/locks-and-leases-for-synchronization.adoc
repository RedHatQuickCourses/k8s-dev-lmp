#  Locks and Leases for synchronization

= Locks and Leases for Synchronization

In a distributed system like Kubernetes, multiple instances of a controller often run in parallel to ensure high availability. However, this introduces the risk of conflicting actions—such as two controllers attempting to modify the same resource simultaneously or performing redundant heavy computations. To ensure system stability and avoid "split-brain" scenarios, we use **Locks and Leases**.

== Understanding Distributed Synchronization

In Kubernetes, we rely on **eventual consistency**. Because we cannot guarantee instantaneous global state, we use primitives that allow processes to agree on who is currently "in charge" of a specific task.

### The Role of the Lease API
A `Lease` is a Kubernetes object (part of the `coordination.k8s.io` API group) that represents a lock. It provides a mechanism for a process to claim ownership of a resource for a specified duration (the `leaseDurationSeconds`).

*   **Heartbeating:** The owner of the lease must periodically update the `renewTime`.
*   **Expiration:** If the owner crashes or network partitions occur, the lease expires. Other candidates can then acquire the lease.
*   **Atomicity:** By using the Kubernetes API server as the source of truth, we leverage its optimistic concurrency control (via `resourceVersion`) to ensure that only one controller successfully claims the lease.

== Leader Election Mechanism

Leader election is the most common use case for Leases. It ensures that out of *N* controller replicas, only one performs the "active" reconciliation, while others remain in standby mode.

[source,go]
----
import (
    "k8s.io/client-go/tools/leaderelection"
    "k8s.io/client-go/tools/leaderelection/resourcelock"
)

// The controller defines a lock on a Lease object
lock := &resourcelock.LeaseLock{
    LeaseMeta: metav1.ObjectMeta{Name: "my-controller-lock", Namespace: "kube-system"},
    Client:    client,
    LockConfig: resourcelock.ResourceLockConfig{
        Identity: podName,
    },
}

// Start the leader election loop
leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
    Lock:            lock,
    ReleaseOnCancel: true,
    LeaseDuration:   15 * time.Second,
    RenewDeadline:   10 * time.Second,
    RetryPeriod:     2 * time.Second,
    Callbacks: leaderelection.LeaderCallbacks{
        OnStartedLeading: func(ctx context.Context) { /* Run controller logic */ },
        OnStoppedLeading: func() { /* Cleanup */ },
    },
})
----

== Hands-on Activity: Observing Leader Election

In this activity, we will deploy a multi-replica deployment and observe how the Lease object manages the leader.

### Prerequisites
*   A running Kubernetes cluster.
*   `kubectl` configured with cluster-admin access.

### Step 1: Create the Lease
Create a manifest to initialize the lock.

[source,yaml]
----
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: example-leader-lock
  namespace: default
----

### Step 2: Simulate Multiple Replicas
Deploy two instances of a sample application that uses the `client-go/tools/leaderelection` library to compete for the `example-leader-lock`.

1.  Deploy the pods: `kubectl apply -f controller-deployment.yaml` (ensure `replicas: 2`).
2.  Check which pod owns the lease:
+
[source,bash]
----
kubectl get lease example-leader-lock -o yaml
----
3.  Observe the `holderIdentity` field.

### Step 3: Trigger a Failover
1.  Identify the leader pod: `kubectl get pods`.
2.  Delete the leader pod: `kubectl delete pod <leader-pod-name>`.
3.  Immediately inspect the Lease object again:
+
[source,bash]
----
kubectl get lease example-leader-lock -o yaml
----
4.  **Observation:** You will see the `holderIdentity` update to the name of the remaining pod once the `leaseDuration` has passed and the new leader performs its first heartbeat.

== Best Practices and Gotchas
*   **Clock Skew:** Never rely on system time for logic; always use the Kubernetes API server's time (via the `Lease` object) to avoid issues with drift.
*   **Fencing:** Distributed locking is not a silver bullet. If your controller performs external I/O (e.g., updating a database outside K8s), ensure that your external systems also respect the lease ownership to prevent "zombie" processes from corrupting state.
*   **Resource Contention:** Avoid creating a unique lease for every single custom resource. Instead, group resources or shard your controllers to minimize API server load.
