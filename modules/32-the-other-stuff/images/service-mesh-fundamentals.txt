In a microservices architecture, every service requires essential networking features like service discovery, load balancing, retries, timeouts, mutual TLS, and telemetry. Implementing these cross-cutting concerns inside each application—across multiple languages and frameworks—is both tedious and error-prone. A service mesh solves this by moving that logic into the infrastructure layer, allowing applications to simply send and receive traffic on localhost, without needing to be aware of the underlying network topology.

The capabilities of a service mesh generally fall into three key categories. First is traffic management, which includes dynamic service discovery, routing, traffic splitting for canary releases and A/B tests, as well as retries, timeouts, circuit breaking, and rate limiting. Second is security, which provides automatic mutual TLS for all service-to-service communication, certificate rotation, and fine-grained access policies based on service identity. Third is observability, which ensures the uniform collection of golden-signal metrics—such as latency, traffic, errors, and saturation—along with distributed traces and access logs across every hop in the mesh.

A service mesh is composed of two primary layers: the data plane and the control plane. The data plane consists of lightweight network proxies, typically Envoy, deployed alongside each service instance. In the traditional sidecar model, every pod gets its own proxy container. These proxies intercept all inbound and outbound traffic to apply routing rules, enforce mutual TLS, and emit telemetry. The control plane acts as a centralized component that configures these proxies at runtime. It translates high-level routing rules and security policies into proxy-specific configurations and manages the distribution of certificates for mutual TLS.

Istio is the most widely adopted service mesh. It is a Cloud Native Computing Foundation graduated project, originally created by Google, IBM, and Lyft. Its control plane is a single binary called `istiod`. This component consolidates earlier functions like Pilot, Citadel, and Galley, and it handles service discovery, certificate generation, and configuration distribution to the Envoy sidecars. Istio provides two types of authentication: Peer authentication for service-to-service mutual TLS, and Request authentication for validating end-user credentials using JSON Web Tokens or OpenID Connect providers.

When it comes to traffic splitting, Istio uses custom resources called `VirtualService` and `DestinationRule` to control routing. For example, you can configure a Virtual Service to send 90 percent of traffic to version one of a service and 10 percent to version two, while using a Destination Rule to define the specific labels for those two versions.

Istio also offers a newer approach called Ambient mode, which eliminates the sidecar container entirely. In this model, a per-node `ztunnel` proxy handles Layer 4 concerns like mutual TLS and basic telemetry for all pods on that node. Optional `waypoint` proxies are then used to handle Layer 7 policies only when they are needed. Ambient mode is highly efficient because it reduces resource overhead and simplifies the pod lifecycle, as there is no longer a sidecar to inject, restart, or drain.

As a final tip, keep in mind that a service mesh does add real operational complexity. Before adopting one, carefully evaluate whether your application genuinely needs mesh-level traffic management, mutual TLS, and observability. For simpler deployments, native Kubernetes NetworkPolicies and the Gateway API may be sufficient to meet your needs.
