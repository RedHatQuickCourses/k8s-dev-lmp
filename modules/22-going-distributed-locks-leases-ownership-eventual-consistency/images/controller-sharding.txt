Leader election is a great tool for high availability, as it allows a standby replica to take over if the active one fails. However, it doesn't provide horizontal scaling, because only one replica is doing the work at any given time. To solve this, we use controller sharding, which distributes reconciliation across multiple instances, with each responsible for a specific subset of resources.

When you have a controller managing thousands of resources, a single reconciler can easily become a bottleneck. Sharding solves this by dividing the resource space so that multiple replicas can reconcile concurrently without conflicting. The primary challenges here are assigning resources to shards consistently, rebalancing those resources when shards are added or removed, and ensuring that child resources correctly follow their parent's assignment.

The Kubernetes controller sharding project offers a common approach to this using labels. Here is how that mechanism works. First, each shard instance announces itself by maintaining a Lease object with a status label, indicating whether it is ready or dead. A sharder webhook then intercepts create and update requests for your resource types. This webhook uses consistent hashing to assign a shard label to each object. It hashes the object key and the shard names onto a virtual ring, assigning the object to the nearest shard. Consequently, each controller instance only watches objects labeled with its own identity. Finally, for child objects with owner references, the system ensures they inherit their parent's shard assignment by hashing the owner's key instead of their own.

When you need to scale down and remove a shard, the instance releases its lease and the sharder marks it as dead. Any orphaned objects have their shard labels removed, allowing the webhook to reassign them to the remaining shards during the next update.

When scaling up by adding a new shard, the process is a bit more coordinated. First, the new shard acquires a lease and is marked as ready. The sharder then identifies which objects should move to this new shard and applies a drain label to them. The current shard stops reconciling those drained objects and removes both the drain and the shard labels. Finally, the webhook reassigns those objects to the new shard. This handoff is critical because it prevents two shards from trying to reconcile the same object at the same time.

A practical, real-world example of this is OpenShift Ingress Controller sharding, which allows multiple ingress controllers to run simultaneously, each responsible for a subset of network routes. You configure this at the infrastructure level using route and namespace selectors on the Ingress Controller resource.

OpenShift supports two main sharding models. The first is a traditional, non-overlapping model where each route is served by exactly one ingress controller. The second is an overlapped model, where routes can match multiple ingress controllers. This allows for complex routing topologies, though it requires careful planning. You might use ingress sharding to separate internal from external traffic, isolate workloads that require different reliability levels, load balance across multiple router instances, or implement blue-green deployment strategies.

An important caution to keep in mind: each ingress controller requires its own dedicated DNS entry. Routers will not forward unknown routes to other routers, so if a route does not match any selector, it will remain unreachable.

When you do use overlapping mode, where multiple controllers serve the same route, each controller writes its own entry into the status ingress array. They do this using atomic list types, which prevents concurrent writers from corrupting each other's status entries.
