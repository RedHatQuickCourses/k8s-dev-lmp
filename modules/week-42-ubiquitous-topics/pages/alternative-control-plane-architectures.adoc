#  Alternative control plane architectures

= Alternative Control Plane Architectures

In standard Kubernetes deployments, the control plane—comprising the `kube-apiserver`, `etcd`, `kube-scheduler`, and `kube-controller-manager`—is typically colocated with the workload cluster or deployed as a dedicated management cluster. However, as Kubernetes expands into edge computing, massive multi-tenancy, and resource-constrained environments, standard architectures often face limitations.

Alternative control plane architectures decouple these components, providing specialized form factors for distinct use cases.

== The Evolution of Control Plane Form Factors

The "one size fits all" approach to the Kubernetes control plane is evolving into a spectrum of architectures tailored to specific operational requirements:

*   **Hosted/Nested Control Planes (HyperShift):** By running the control plane as a workload inside an existing OpenShift cluster, HyperShift isolates the control plane into a separate namespace. This provides rapid cluster provisioning and high density, as the control plane for a "guest" cluster is just a set of pods.
*   **Logical Control Planes (kcp):** Designed as a "Kubernetes-like" system, `kcp` provides a control plane that is not tied to a single cluster. It acts as a universal API surface that can project resources into multiple underlying physical clusters, ideal for global scale and multi-cluster abstraction.
*   **Single-Binary & Edge Optimized (MicroShift, k3s, k0s):** These architectures collapse the control plane components into a single, lightweight binary. 
    *   **MicroShift:** An enterprise-ready, minimal-footprint distribution of OpenShift designed specifically for edge devices.
    *   **k3s/k0s/microk8s:** Optimized for low-resource environments (IoT, CI/CD pipelines) by stripping away legacy code and optimizing storage engines for small-scale deployments.

== Comparative Architecture Overview

| Architecture Type | Use Case | Primary Advantage |
| :--- | :--- | :--- |
| **HyperShift** | Massive multi-tenancy | Resource efficiency; fast provisioning. |
| **kcp** | Global orchestration | API-first design; multi-cluster management. |
| **MicroShift/k3s** | Edge / IoT | Low memory footprint; operational simplicity. |

== Hands-On Activity: Analyzing Component Density

In this activity, you will compare the footprint of a standard control plane against a lightweight alternative.

=== Prerequisites
*   A running Kubernetes cluster (e.g., `kind` or `minikube`).
*   `kubectl` installed and configured.

=== Step 1: Inspect Standard Control Plane Footprint
1. Check the resource footprint of your current control plane:
+
[source,bash]
----
kubectl get pods -n kube-system -l component=kube-apiserver
kubectl top pods -n kube-system
----
2. Note the resource overhead required to maintain the etcd and API server processes.

=== Step 2: Simulate Minimal Architecture Concepts
Understand the difference by examining a single-binary distribution (like k3s):
1. Download a k3s-compatible environment or inspect the process tree of a minimal distribution:
+
[source,bash]
----
# On a host running a minimal distribution, list processes
ps aux | grep -E "kube-apiserver|k3s"
----
2. Observe how `k3s` encapsulates the controller-manager, scheduler, and API server into a single process, whereas the standard cluster runs them as distinct, heavy-weight pods.

=== Troubleshooting Guidance
*   **Observability:** When using nested control planes like HyperShift, remember that logs for your guest cluster control plane are stored as container logs within the management cluster. Use `kubectl logs -n <guest-cluster-ns> <control-plane-pod>` to debug.
*   **Consistency:** In distributed "logical" control planes (like `kcp`), latency between the control plane and the workload cluster can impact the reconciliation loop. Monitor the `Informers` and `SyncTarget` status to ensure eventual consistency is being maintained.
