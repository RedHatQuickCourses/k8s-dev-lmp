#  HyperShift and kcp

= Advanced Control Plane Architectures: HyperShift and kcp

As Kubernetes matures, the requirement for diverse deployment environments—ranging from hyperscale cloud clusters to resource-constrained edge devices—has led to the evolution of the control plane itself. This section explores two prominent architectural patterns: **HyperShift** and **kcp**.

== HyperShift: Hosted Control Planes
HyperShift (also known as Hosted Control Planes for OpenShift) is an architecture designed to decouple the control plane from the worker nodes. In standard Kubernetes, the control plane (API server, etcd, scheduler, controllers) runs on the same infrastructure as the worker nodes. 

In the HyperShift model:
* **Management Cluster:** Runs the control plane components as pods within a standard Kubernetes/OpenShift cluster.
* **Guest Cluster:** Contains only the worker nodes (kubelet and kube-proxy).

=== Why HyperShift?
1. **Reduced Resource Overhead:** By centralizing control planes, you eliminate the need to provision dedicated control plane nodes for every single cluster, significantly reducing the "tax" of running many small clusters.
2. **Speed:** Because control planes are just sets of pods, spinning up a new "cluster" is significantly faster—often taking seconds rather than minutes.
3. **Isolation:** Control planes are isolated by namespace/pod security boundaries, allowing for dense multi-tenancy.

== kcp: The Kubernetes-like Control Plane
While HyperShift is about managing standard Kubernetes control planes, **kcp** is a project that provides a "Kubernetes-like" API surface without being a full-blown Kubernetes cluster. It is designed for scenarios where you need the Kubernetes API (and its powerful controller ecosystem) but don't need the overhead of nodes, pods, or the kubelet.

=== Core Concepts of kcp
* **API-Centric:** kcp focuses solely on the API server, etcd, and the controller-runtime. It provides the "Kubernetes experience" (CRDs, controllers, workspaces, and virtual clusters) without managing physical infrastructure.
* **Logical Clusters (Workspaces):** kcp introduces the concept of workspaces, allowing for massive multi-tenancy where a single kcp instance can host thousands of virtual control planes.
* **Synchronization:** kcp uses *syncer* agents that watch resources in the kcp control plane and push those states to physical "target" clusters. This allows you to manage thousands of downstream clusters from a single, unified API endpoint.

== Comparative Summary

[cols="1,1,1", options="header"]
|===
| Feature | HyperShift | kcp
| **Primary Goal** | Efficient management of full K8s clusters | API-centric management of distributed resources
| **Architecture** | Control plane as Pods | Specialized API server + Syncer agents
| **Use Case** | Multi-cluster OpenShift/K8s management | Global fleet management and SaaS control planes
| **Workload Type** | Full K8s Workloads (Pods) | Abstracted resources synchronized to targets
|===

== Troubleshooting Tips
* **Latency:** When dealing with remote control planes (HyperShift), network latency between the Management and Guest control plane can affect reconciliation times. Always check `status.conditions` to see if a controller is stuck in a "Progressing" state.
* **Context switching:** When debugging, ensure your `KUBECONFIG` is correctly set. Use `kubectl config current-context` to confirm you are targeting the Management plane rather than accidentally running commands against the Guest/Target plane.
