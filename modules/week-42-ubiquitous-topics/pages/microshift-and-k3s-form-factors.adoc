#  Microshift and k3s form factors

= MicroShift and k3s Form Factors

In the evolution of Kubernetes, the "one-size-fits-all" model of a standard control plane often proves too resource-heavy for constrained environments. When moving from the data center to the edge—industrial IoT gateways, retail kiosks, or automotive systems—engineers must prioritize footprint, resource efficiency, and simplified lifecycle management.

This section explores two prominent lightweight Kubernetes distributions: **k3s** and **MicroShift**, which are designed specifically for these "small-footprint" scenarios.

== k3s: The Lightweight Distribution
Developed by Rancher (now SUSE), k3s is a highly available, certified Kubernetes distribution designed for production workloads in unattended, resource-constrained, and remote locations.

=== Key Characteristics
*   **Single Binary:** k3s packages all components (kube-apiserver, kube-scheduler, kube-controller-manager, kubelet, and kube-proxy) into a single, small binary (< 100MB).
*   **SQLite by Default:** While it supports external databases like etcd, it defaults to SQLite for smaller setups, significantly reducing the memory overhead compared to a full etcd cluster.
*   **Component Consolidation:** It removes legacy code, cloud-provider plugins, and unnecessary drivers found in upstream Kubernetes, focusing strictly on the requirements of edge compute.
*   **Optimized for ARM:** k3s has first-class support for ARM64 and ARMv7, making it ideal for devices like the Raspberry Pi or specialized industrial ARM hardware.

== MicroShift: OpenShift at the Edge
MicroShift is a foundational project that brings the operational consistency of OpenShift to small-scale environments. It is effectively a "stripped-down" version of OpenShift designed to run on single-node or limited-resource edge devices.

=== Key Characteristics
*   **OpenShift Consistency:** MicroShift provides a subset of the OpenShift Container Platform (OCP) APIs. This allows developers to use the same security policies, image streams, and workload definitions they use in their data center OpenShift clusters.
*   **Integrated Optimization:** Unlike standard Kubernetes, where you might bolt on monitoring or networking tools, MicroShift comes with pre-configured, optimized components that are tuned for the limited resource profile of edge hardware.
*   **Life-cycle Alignment:** It focuses on being easy to update and manage, fitting into the "immutability" patterns required for remote edge nodes where manual troubleshooting is difficult.
*   **Comparison to HyperShift:** While HyperShift (Hosted Control Planes) separates the control plane into a management cluster to gain density, MicroShift is designed for *standalone* local operation where connectivity to a central management hub may be intermittent.

== Comparative Analysis

| Feature | k3s | MicroShift |
| :--- | :--- | :--- |
| **Primary Goal** | Lightweight standard Kubernetes | Edge-optimized OpenShift API |
| **Footprint** | Extremely low (Single binary) | Low (Optimized OCP subset) |
| **API Compliance** | CNCF Certified | OCP Sub-set (High compatibility) |
| **Best For** | General purpose IoT/Small clusters | Enterprise edge requiring OCP parity |

== Hands-on Activity: Observing Footprint
In this exercise, you will compare the memory footprint of a lightweight cluster against a standard distribution.

=== Step 1: Deploy k3s
On a Linux-based virtual machine or node, install k3s using the quick-start script:

[source,bash]
----
curl -sfL https://get.k3s.io | sh -
----

=== Step 2: Analyze Process Memory
Inspect the memory usage of the Kubernetes components. Note the consolidation of the server process:

[source,bash]
----
# View the consolidated server process
ps aux | grep k3s
# Check memory consumption of the core components
top -p $(pgrep -f "k3s server")
----

=== Step 3: Discussion
Reflect on the `ps` output. 
*   **Question:** How many distinct processes do you see compared to a standard `kubeadm` install (which would show separate processes for `etcd`, `kube-apiserver`, etc.)?
*   **Observation:** You will notice that k3s runs as a single process, reducing the memory pressure caused by overhead in inter-process communication and multiple Go runtimes.

== Troubleshooting Tips
*   **Resource Exhaustion:** If your edge device is failing to schedule pods, check `journalctl -u k3s` or `journalctl -u microshift` for OOM (Out-of-Memory) signals.
*   **Cgroups:** Ensure the underlying OS has `cgroup v2` enabled, as both distributions rely heavily on modern kernel resource management to keep their footprint small.
*   **Network:** When deploying at the edge, ensure that your firewall allows the specific ports required for the control plane, as these light distributions often strip out complex network policy implementations to save RAM.
