At its core, Kubernetes is an API-centric, declarative configuration management and container orchestration system. Rather than issuing imperative commands to tell the server what to do, you interact with the system by declaring the desired state of your resources as pure data.

The heart of the control plane is the API server. This server acts as a central coordination point and persists your desired state into a key-value store called etcd. To make reality match those declarations, Kubernetes relies on an ecosystem of asynchronous controllers. These controllers continuously watch the API server for changes, compare the current observed state of the world to your desired state, and actively reconcile any differences. This separation of responsibilities—where the API server maintains the shared state and independent controllers actuate it—is the same fundamental architecture you will use and extend when building your own custom operators.

To better understand how this system functions, it helps to think of Kubernetes in terms of three distinct layers.

First is the Resource Schema layer. This defines what types of resources exist and the shape they take. In Kubernetes, this is expressed through API group-version-kind definitions, Protocol Buffer schemas for built-in types, and Open API v3 validation schemas for custom resources.

Second is the Concrete Resource Syntax layer. This consists of the raw YAML or JSON data that you author and submit to the API server. Keep in mind that Kubernetes deliberately accepts only fully-realized resource definitions. It pushes abstraction—such as templating and parameterization—to external tools like Helm, Kustomize, or general-purpose programming languages.

Third is the Convergence Engine. These are the controllers that take a concrete set of resource declarations and actuate the managed system to match them. Kubernetes has perhaps the most explicit notion of this layer of any declarative system, embodied directly in its controller architecture.

This layered model clarifies why Kubernetes separates its concerns the way it does. The API server owns the first two layers—the schema and the storage of declared state—while the controllers independently implement the third layer by making reality converge.
