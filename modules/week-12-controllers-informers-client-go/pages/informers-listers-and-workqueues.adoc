#  Informers, listers, and workqueues

= Week 1.2: Informers, Listers, and Workqueues

In the Kubernetes controller pattern, the goal is to drive the current state of the system toward a desired state. To do this efficiently without overwhelming the `kube-apiserver`, we rely on `client-go` components that optimize communication and event processing.

== The Controller Architectural Pattern

The `client-go` library provides the plumbing required to build high-performance controllers. At its heart, the architecture is designed to handle asynchronous event propagation.

### The Role of Components
You can visualize the data flow as a pipeline:

*   **Informers:** Acting as the "eyes" of the controller, Informers watch the API server for resource changes. They use long-polling (or HTTP/2 streaming) to receive events (Add, Update, Delete) and keep a local state.
*   **Listers:** These provide a read-only interface to the local cache maintained by the Informer. Instead of querying the `kube-apiserver` every time you need to check an object, you query the local cache via the Lister, significantly reducing latency and API server load.
*   **Workqueues:** These act as buffers for event processing. When an Informer detects a change, it pushes the *key* (namespace/name) of the affected object into a Workqueue. The controller then picks up these keys to perform reconciliation.

[IMPORTANT]
====
**Queues are strictly FIFO.** Unlike a stack (LIFO), a workqueue ensures that the oldest events are processed first, maintaining sequential integrity for state changes.
====

== How Data Flows: The Synchronization Loop

1.  **Reflector:** The Reflector watches the API server for a specific resource type. When it detects an event, it places the object into a `DeltaFIFO` queue.
2.  **Informer:** The Informer processes items from the `DeltaFIFO` queue, updates the local cache (Store), and triggers registered Event Handlers.
3.  **Event Handler:** Usually, the handler simply takes the object's key and adds it to the **Workqueue**.
4.  **Worker:** The controller's `processNextWorkItem` function pulls the key from the Workqueue and executes the `Reconcile` logic.

== Hands-On Activity: Analyzing Queue Behavior

In this exercise, you will observe how a `workqueue` handles multiple updates to the same object.

=== Prerequisites
*   Go installed (1.21+)
*   `k8s.io/client-go` module initialized in your project

=== Steps

1.  **Initialize the Workqueue:**
    Inside your controller logic, create a new rate-limiting queue:
    [source,go]
    ----
    queue := workqueue.NewNamedRateLimitingQueue(workqueue.DefaultControllerRateLimiter(), "my-controller")
    ----

2.  **Enqueue a Key:**
    In your Informer's `AddFunc` or `UpdateFunc`, extract the key:
    [source,go]
    ----
    key, err := cache.MetaNamespaceKeyFunc(obj)
    if err == nil {
        queue.Add(key)
    }
    ----

3.  **Implement the Worker:**
    Create a loop that pulls items and processes them.
    [source,go]
    ----
    func (c *Controller) processNextItem() bool {
        key, quit := c.queue.Get()
        if quit { return false }
        defer c.queue.Done(key)

        // Use the Lister to get the object from local cache
        obj, exists, _ := c.lister.GetByKey(key.(string))
        
        // ... perform reconciliation logic ...

        return true
    }
    ----

4.  **Error Handling and Requeueing:**
    If your reconciliation fails, use `queue.AddRateLimited(key)` to put the item back into the queue. The RateLimiter will implement exponential backoff, preventing your controller from entering a hot-loop if an error persists.

== Troubleshooting Gotchas

*   **Cache Inconsistency:** If your controller reads from a Lister but the cache hasn't synced yet (e.g., during controller startup), you will get empty results. Always ensure `cache.WaitForCacheSync` is called before starting your workers.
*   **Blocking the Queue:** Never perform long-running blocking operations (like calling external APIs) directly inside the `Reconcile` loop. If the worker blocks, the queue depth will grow, and your controller will fall behind the cluster state.
*   **Key Overwriting:** If a resource is updated rapidly, the queue only needs to store the key. The worker will always fetch the *latest* version from the cache when it eventually processes the key, effectively "collapsing" intermediate states.
