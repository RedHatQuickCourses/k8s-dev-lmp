#  Managing resource Requests and Limits

= Managing Resource Requests and Limits

In the Kubernetes ecosystem, the `kube-scheduler` is responsible for placing pods onto nodes that have sufficient resources to accommodate them. To perform this task effectively, Kubernetes relies on the definitions of **Requests** and **Limits** specified within your Pod manifests. Understanding these mechanisms is fundamental to achieving cluster stability and efficient bin-packing.

== Theoretical Overview

Resources in Kubernetes are primarily managed based on CPU (measured in `millicores`) and Memory (measured in `bytes`).

=== Requests: The Guaranteed Floor
A **Request** is the amount of resource that a container is guaranteed to have. When the scheduler decides which node a pod will land on, it sums up the `requests` of all containers in the pod and ensures the node has that much capacity available. 
* If the node does not have enough unallocated requested resources, the pod will remain in a `Pending` state.

=== Limits: The Hard Ceiling
A **Limit** defines the maximum amount of a resource a container is allowed to consume.
* **CPU:** If a container exceeds its CPU limit, it is throttled, but it will not be terminated.
* **Memory:** If a container attempts to exceed its memory limit, it may trigger an Out-Of-Memory (OOM) kill, causing the container to restart.

[IMPORTANT]
====
Always define both `requests` and `limits`. If a container specifies a limit but no request, Kubernetes automatically sets the request equal to the limit. If neither is specified, the pod is assigned a `BestEffort` Quality of Service (QoS), making it the first candidate for eviction during node resource pressure.
====

== Hands-On Activity: Configuring Resource Constraints

In this activity, you will define resource constraints for a simple NGINX deployment and observe how they affect the scheduling lifecycle.

=== Step 1: Create a Resource-Constrained Pod
Create a file named `resource-pod.yaml` with the following content:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
  - name: nginx-container
    image: nginx
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
----

=== Step 2: Apply and Verify
Apply the configuration to your cluster:

[source,bash]
----
kubectl apply -f resource-pod.yaml
----

Verify the resources assigned to the container by inspecting the pod description:

[source,bash]
----
kubectl describe pod resource-demo | grep -A 2 Resources
----

=== Step 3: Observe Scheduling Behavior
1. **Under-provisioning:** Try to create a pod with an impossibly high request (e.g., `cpu: "100"`).
2. Run `kubectl get pods` and notice the pod status remains `Pending`.
3. Run `kubectl describe pod <pod-name>` to see the `FailedScheduling` event, which confirms the scheduler could not find a node with sufficient capacity.

== Troubleshooting Tips
* **QoS Classes:** Kubernetes classifies pods into `Guaranteed`, `Burstable`, and `BestEffort` based on your requests/limits. Use `kubectl get pod <name> -o yaml` and look for `status.qosClass` to debug eviction issues.
* **CPU Throttling:** If your application performance is sluggish despite low CPU usage, check for throttling. You can monitor the `container_cpu_cfs_throttled_seconds_total` metric via Prometheus to see if your `limits` are set too low.
* **OOMKills:** If your pod crashes frequently, check the exit code:
[source,bash]
----
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].state.terminated.reason}'
----
If it returns `OOMKilled`, you must increase your memory `limits`.
