In a standard Kubernetes cluster, the control plane—including the API server, etcd, controller manager, and scheduler—runs alongside your workload nodes. While this model works well for general-purpose clusters, it is not the only option. As Kubernetes expands into multi-tenant platforms, edge computing, and resource-constrained devices, you will encounter alternative architectures that trade off management overhead, resource footprint, provisioning speed, and operational simplicity.

Let’s look at these alternatives, starting with HyperShift.

HyperShift implements what we call "hosted control planes." In this architecture, the control plane for each tenant cluster runs as a set of pods inside a central management cluster. Meanwhile, the tenant's worker nodes form a separate workload cluster that connects over the network. The management cluster treats each hosted control plane like any other workload.

There are three primary benefits to this approach. First, provisioning is much faster because you are deploying pods rather than bootstrapping dedicated machines. Second, it reduces per-cluster overhead by sharing control-plane nodes across tenants, which removes the need for a three-machine minimum for etcd. Finally, it provides centralized management, allowing you to perform upgrades, patches, and certificate rotations in one place for all hosted clusters. HyperShift is the foundation of Red Hat OpenShift's hosted control plane offerings.

Next is kcp, a Kubernetes-like control plane that serves as a generic API platform without scheduling workloads. It provides the full suite of Kubernetes API machinery—such as CRDs, RBAC, and admission webhooks—but it has no concept of nodes, pods, or kubelets.

kcp introduces three unique concepts: First, workspaces, which are lightweight, isolated API scopes that enable massive multi-tenancy. Second, transparent multi-cluster scheduling, where a "syncer" agent distributes work from the kcp workspace to physical clusters. And third, API export and binding, which allows platform teams to publish reusable APIs for application teams. Essentially, kcp separates the "what"—the API resources—from the "where"—the physical clusters running the workloads.

Now, let’s consider MicroShift. This is a minimal Kubernetes distribution from Red Hat designed specifically for edge and resource-constrained environments. It packages all control-plane components and an embedded etcd into a single binary that runs as a systemd service. It is designed for devices with as little as two CPU cores and two gigabytes of RAM. Because it maintains compatibility with OpenShift APIs, your workloads and policies work just as they would on a full cluster. It is also built for standalone operation, making it ideal for locations with intermittent or no connectivity.

Finally, we have k3s, a lightweight, CNCF-certified distribution originally created by Rancher. Like MicroShift, it bundles everything into a single, small binary—roughly 70 megabytes in size. By default, it uses SQLite instead of etcd, which significantly reduces memory overhead. It is optimized for ARM architecture, making it a great fit for Raspberry Pi and industrial hardware. It also comes "batteries included," shipping with built-in ingress controllers and DNS, making it easy to deploy with a single command.

To summarize how these architectures differ, consider the following. While a standard Kubernetes setup relies on self-hosted control planes on dedicated nodes and requires at least three nodes for high availability, HyperShift moves that control plane into a management cluster. MicroShift and k3s, on the other hand, consolidate the control plane into a single binary, with MicroShift targeting resource-constrained enterprise environments and k3s providing a lightweight option for IoT, dev, and CI/CD workflows.

It is important to remember that these architectures are not mutually exclusive. A platform team might use HyperShift in the data center to manage hundreds of tenant clusters, while deploying MicroShift or k3s on edge devices. Your choice should ultimately depend on where the control plane needs to live, how many clusters you require, and the specific resource constraints at each location.
