In this exercise, you will extend the controller you built in the previous session so that only one replica is active at a time. By implementing leader election, you ensure that even if multiple copies of your controller are running, they coordinate to avoid redundant work. By the end of this lab, you will run two copies of your controller and observe a live failover.

First, ensure you have completed the previous exercise and that your project directory is ready. If you prefer to keep your previous work intact, feel free to create a copy of your project directory before proceeding.

To implement leader election, we will make three specific changes to your `main.go` file. First, we will update the imports to include the leader-election and lease packages. Second, we will move your existing reconcile pipeline into a new function named `runController`, which allows it to start and stop cleanly. Finally, we will rewrite the `main` function to build a `LeaseLock` and hand control to the `leaderelection.RunOrDie` function. This ensures that your controller logic only executes on the instance that successfully holds the lease. Note that your `processNextItem` and `reconcile` functions will remain exactly as they were.

To begin, update the imports in your `main.go` file. You will need to add the context, log, operating system, time, and the necessary leader election packages from `client-go`. You can also remove the direct channel handling, as we will now be using the context package to manage lifecycle signals.

Next, replace your `main` function and add the `runController` function. The new `main` function builds your clientset, constructs a `LeaseLock` with a unique identity based on the process ID, and initializes the `leaderelection.RunOrDie` config. Within the callbacks, we define what happens when an instance starts leading, stops leading, or observes a new leader. 

The `runController` function simply wraps the reconciliation logic you previously had in `main`. It initializes the informers, starts the workqueue, and ensures the controller shuts down gracefully when the context is cancelled. Keep in mind that timing parameters are important here: the `LeaseDuration` must be greater than the `RenewDeadline`, which in turn must be greater than the `RetryPeriod`. Setting these values too low can cause instability, while setting them too high can delay the failover process.

Now, let's build and run the first instance. Run the command `go mod tidy` to clean up your dependencies, followed by `go build`, and then start your controller with `go run main.go`. You should see a log message indicating that your process has acquired the lease and started the controller.

With the first instance running, open a second terminal and start another instance of your controller. You will see that the second instance recognizes the first one as the current leader and remains in a standby state, waiting for the lease to become available. You can verify this by opening a third terminal and using `kubectl get lease my-controller-lock -n default -o yaml` to inspect the status of the lease and identify the current holder.

Finally, test the failover by stopping the first instance using Control-C in your first terminal. Within approximately 15 seconds, the second instance will detect the expired lease, acquire it, and begin reconciling. You can confirm this transition by checking the lease again with `kubectl`; you will see that the holder identity has updated and the lease transitions counter has incremented.

As a final reminder, remember that the leader election package does not strictly guarantee single-leader semantics in all edge cases. If a leader experiences a significant pause, it might briefly believe it is still the leader even after another has taken over. This is why it is critical to rely on Kubernetes' built-in optimistic concurrency—where updates are rejected if they use a stale resource version—to protect your system's consistency. When you are finished, stop your remaining controller instance with Control-C.
