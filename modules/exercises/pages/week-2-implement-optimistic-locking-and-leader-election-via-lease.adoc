#  Week 2: Implement optimistic locking and leader election via Lease

= Week 2: Implementing Distributed Coordination

When running multiple replicas of a controller for high availability, you face a significant challenge: "split-brain" scenarios. If two controllers attempt to reconcile the same resource simultaneously, they can cause race conditions, unnecessary API churn, or conflicting state changes.

To solve this, we use **Leader Election** based on Kubernetes `Lease` objects.

== Understanding Distributed Synchronization

In Kubernetes, we achieve coordination through the `coordination.k8s.io` API group.

*   **Lease:** A `Lease` object represents a lock held by a specific participant in a distributed system. It contains a `holderIdentity` and a `renewTime`.
*   **Optimistic Locking:** Instead of locking a database row (which is risky in distributed systems), we use the `resourceVersion` field of the `Lease` object. If the version has changed since we last read it, the update fails, forcing the controller to retry.
*   **Leader Election:** This is essentially a "race" to claim and maintain a `Lease`. The leader periodically updates the `renewTime`. If the leader crashes, the `renewTime` expires, allowing a follower to take over.

== Hands-on Activity: Adding Leader Election to your Controller

In this exercise, we will extend your existing `client-go` controller to ensure only one instance is active at a time using the `client-go/tools/leaderelection` package.

=== Prerequisites

*   A functional controller built with `client-go`.
*   `leaderelection` package imported: `k8s.io/client-go/tools/leaderelection`
*   `resourcelock` package imported: `k8s.io/client-go/tools/leaderelection/resourcelock`

=== Step 1: Define the Lock Identity

Each controller instance needs a unique identity (usually its Pod name).

[source,go]
----
import (
    "os"
    "k8s.io/client-go/tools/leaderelection/resourcelock"
)

// Get unique ID for this instance
id, _ := os.Hostname()
----

=== Step 2: Configure the Lease Lock

We define a `LeaseLock` that tells Kubernetes which object to use to track the leader.

[source,go]
----
lock := &resourcelock.LeaseLock{
    LeaseMeta: metav1.ObjectMeta{
        Name:      "my-controller-lock",
        Namespace: "default",
    },
    Client: clientset.CoordinationV1(),
    LockConfig: resourcelock.ResourceLockConfig{
        Identity: id,
    },
}
----

=== Step 3: Start the Leader Election Loop

The `leaderelection.RunOrDie` function handles the lifecycle of the lock. It provides callbacks to trigger your controller logic only when the lock is acquired.

[source,go]
----
leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
    Lock:            lock,
    ReleaseOnCancel: true,
    LeaseDuration:   15 * time.Second,
    RenewDeadline:   10 * time.Second,
    RetryPeriod:     2 * time.Second,
    Callbacks: leaderelection.LeaderCallbacks{
        OnStartedLeading: func(ctx context.Context) {
            // This is where you start your Controller's Run/Reconcile logic
            runMyController(ctx)
        },
        OnStoppedLeading: func() {
            log.Printf("Leader lost, shutting down.")
            os.Exit(0)
        },
        OnNewLeader: func(identity string) {
            log.Printf("New leader elected: %s", identity)
        },
    },
})
----

== Troubleshooting and Best Practices

*   **Lease Duration:** Do not set this too short (frequent network jitter will cause constant re-elections) or too long (failover will be slow if a node dies).
*   **Eventual Consistency:** Remember that the controller state machine must be **idempotent**. If the leader crashes, the new leader will read the current state of your `Memcached` resources and reconcile them from scratch.
*   **Debugging:** Use `kubectl get lease my-controller-lock -o yaml` to inspect the `holderIdentity` and verify which replica currently holds the lock.
