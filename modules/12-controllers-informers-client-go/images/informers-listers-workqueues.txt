To build an effective Kubernetes controller, you need three foundational components: "eyes" to observe changes, "memory" to recall the current state, and a "task list" to schedule your work. In the client-go library, these roles correspond to Informers, Listers, and Workqueues.

Let’s look at the first component: Informers, which act as the eyes of your controller. An informer watches the API server and maintains a local cache of the resources it tracks. Under the hood, this relies on a Reflector that performs two key operations. First, it performs an initial "list" that fetches every existing object of the watched resource type and records its resource version. Second, it runs a continuous "watch" that streams incremental changes starting from that resource version. Every object retrieved during the initial list is treated as new and passed to the add function handler, while subsequent creations, modifications, and deletions are routed to their respective add, update, or delete functions. Most developers use the SharedIndexInformer, which ties the reflector, the DeltaFIFO, the event processor, and the indexer together.

Next, we have Listers, which serve as the memory of your controller. A lister is a thin, read-only wrapper around your local cache, or indexer. Instead of making a live API call every time you need to retrieve an object, you simply query the lister. This read happens entirely in memory within your process, providing an immediate response without adding network latency or load to the API server. Keep in mind that for controller-runtime, the standard client dot-Get method uses a cache-backed client by default, which functions just like a lister. You should generally only use direct API calls when you need a strongly consistent, uncached read, such as immediately before a write to avoid conflicts.

Third, we have Workqueues, which function as your task list. When an event handler fires, it does not run the reconciliation logic immediately. Instead, it extracts the object's unique key, which is the namespace and name, and enqueues it into a workqueue. The reconciliation loop then processes these keys independently. This design offers three critical benefits. First, it provides deduplication; if multiple updates arrive for the same object rapidly, the queue collapses them into a single entry, so you only reconcile against the current state. Second, it offers rate limiting, where failed items are requeued with an exponential backoff to ensure a broken resource does not overwhelm your system. Third, it ensures serialized processing per key; even if you have multiple worker goroutines running, the queue guarantees that only one worker processes a specific key at any given time.

When implementing these, follow the established Kubernetes controller guidelines. Always operate on one item at a time using a workqueue, and remember that there is no ordering guarantee across distinct watches. Because your controller may be offline for periods, design your logic to be level-driven rather than edge-driven—always reconcile based on the current state of the world, not just the event that triggered the process. Use SharedInformers to save server resources, and always create a deep copy of objects before modifying them, as caches are shared across multiple controllers. Before processing, always call wait-for-cache-sync to ensure your cache is populated, and always expect that other actors may be modifying resources simultaneously. Finally, to ensure high availability, use leader election so that only one instance of your controller is active at a time.

Finally, let’s discuss resyncs. Informers can optionally re-list all cached objects on a periodic interval. During this process, the informer calls the update function for every object in the cache, even if nothing has changed on the API server. This serves as a safety net to ensure that if a reconciliation was previously missed, the controller gets another chance to process the object. 

It is important to note that a resync does not make a new list call to the API server; it simply re-delivers the existing cached objects. If you want to avoid redundant reconciliations, you can compare the resource versions of the objects in your update handler, but be careful—skipping too aggressively might prevent the retry of previously failed items.
