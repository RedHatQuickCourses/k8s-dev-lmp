#  Kubernetes control plane and API server role

= Kubernetes Control Plane and API Server Role

The Kubernetes control plane is the "brain" of the cluster. It orchestrates the cluster state, manages scheduling, and maintains the desired state of all workloads. At the heart of this system lies the `kube-apiserver`, the front door to the cluster that exposes the Kubernetes API.

== The Control Plane Architecture

The control plane consists of several core components working in concert:

*   **kube-apiserver:** The central hub that processes REST requests, performs authentication/authorization, and persists cluster state to `etcd`.
*   **etcd:** A strongly consistent, distributed key-value store used as Kubernetes' backing store for all cluster data.
*   **kube-scheduler:** Watches for newly created Pods with no assigned node and selects a node for them to run on.
*   **kube-controller-manager:** Runs controller processes (e.g., Node Controller, Job Controller) that regulate the state of the cluster by reconciling current state with desired state.

== The Role of kube-apiserver

The `kube-apiserver` is the only component that communicates directly with `etcd`. All other components (and external users) communicate exclusively with the API server. 

=== The Request Lifecycle
When a request enters the `kube-apiserver`, it traverses a series of plugin layers before reaching storage. This pipeline ensures security, integrity, and operational fairness:

1.  **Authentication:** Validates the identity of the user or service account (e.g., OIDC, X.509 certs, or tokens).
2.  **Audit:** Logs the request details for security and compliance.
3.  **Impersonation:** Allows users to perform actions on behalf of another user if authorized.
4.  **Priority & Fairness:** Manages request flow to prevent the API server from being overwhelmed.
5.  **Authorization:** Determines if the authenticated user has permission to perform the specific action (RBAC, ABAC, Webhooks).
6.  **Admission:** Enforces policies via `Validating` or `Mutating` webhooks.
7.  **Storage:** Writes the object to `etcd` or retrieves the requested data.

[NOTE]
====
Admission webhooks (Validating and Mutating) are executed only during `CREATE`, `UPDATE`, or `DELETE` operations. They are *not* triggered during `GET` or `LIST` operations.
====

== Hands-on Activity: Inspecting the API Flow

In this exercise, you will observe the API server's role in processing a simple resource creation.

=== Prerequisites
* A running Kubernetes cluster (e.g., Minikube, Kind, or OpenShift).
* `kubectl` installed and configured.

=== Step 1: Enable Audit Logging
To see how the API server processes requests, you can look at the audit logs. If you have access to the control plane, inspect the log file (usually defined in the `/etc/kubernetes/manifests/kube-apiserver.yaml` configuration).

[source,bash]
----
# Check the audit log location
grep "audit-log-path" /etc/kubernetes/manifests/kube-apiserver.yaml
----

=== Step 2: Create a Resource and Trace
Create a simple ConfigMap and observe how the API server registers the intent.

1. Create the manifest:
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: test-config
data:
  key: value
----

2. Apply it with verbose output to see the interaction:
[source,bash]
----
kubectl apply -f configmap.yaml -v=9
----

3. Observe the `PUT` or `POST` requests being sent to the `/api/v1/namespaces/default/configmaps/test-config` endpoint. 

=== Step 3: Verification
Use `kubectl` to confirm that the `kube-apiserver` has persisted the object to `etcd`:

[source,bash]
----
# Check the status of the resource
kubectl get configmap test-config -o json
----

====
For deep dives into the lifecycle, refer to the "Life (or Death) of a Kubernetes API Request" documentation, which maps every step of the plugin layer chain.
