#  Asynchronous controller reconciliation patterns

= Asynchronous Controller Reconciliation Patterns

The power of Kubernetes lies in its ability to transition a system from its current state to a desired state without human intervention. This capability is powered by the **Reconciliation Pattern**, an asynchronous control loop that continuously monitors the state of the cluster and acts to resolve discrepancies.

== The Control Loop Mechanism

At the heart of every Kubernetes controller is an asynchronous control loop. Unlike traditional procedural scripts that execute tasks in a linear sequence, a controller acts as an autonomous agent that follows a cycle of **Observe, Analyze, and Act**.

[source,text]
----
for {
  1. Observe: Get current state from the API Server (via Cache/Informer).
  2. Analyze: Compare current state with the desired state (Spec).
  3. Act: Execute operations (CRUD) to align current state with desired state.
}
----

=== Key Characteristics
*   **Asynchronous:** The controller does not wait for a specific request to trigger an action; it responds to changes in the cluster state whenever they occur.
*   **Declarative:** The controller focuses on *what* the end state should be (the Spec), not *how* to get there.
*   **Idempotency:** Because the loop runs repeatedly, it is critical that actions are idempotent. Applying the same action multiple times must result in the same state, preventing side effects or resource duplication.

== Event Propagation and Synchronization

In a large cluster, the API server would be overwhelmed if every controller requested the state of all resources every few milliseconds. To solve this, Kubernetes uses a **Shared Informer** architecture.

=== The Role of the Cache
Controllers do not talk directly to the `kube-apiserver` for every reconciliation cycle. Instead, they utilize a local cache maintained by `client-go`.
1.  **List and Watch:** The informer performs an initial `List` of objects and then opens a `Watch` stream to receive incremental updates (Add, Update, Delete events).
2.  **Event Handling:** These events are processed and stored in a local, thread-safe cache (store).
3.  **Efficiency:** When the controller needs the current state, it fetches the object from the local cache rather than making a network call to the API server.

== Hands-on Activity: Observing Reconciliation

In this activity, we will simulate the conceptual flow of a reconciliation loop.

=== Prerequisites
*   A running Kubernetes cluster (e.g., Minikube or Kind).
*   `kubectl` installed and configured.

=== Step 1: Simulate the "Desired State"
Create a simple manifest that represents our desired state.

[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: reconciliation-demo
data:
  status: "active"
----

Apply it: `kubectl apply -f demo.yaml`

=== Step 2: The Manual "Reconcile" Loop
We will simulate the controller's logic in a bash loop. Open a terminal and run the following command to mimic an asynchronous controller watching for changes:

[source,bash]
----
while true; do
  echo "--- Checking state at $(date) ---"
  # Observe
  CURRENT=$(kubectl get cm reconciliation-demo -o jsonpath='{.data.status}')
  
  # Analyze
  if [ "$CURRENT" != "active" ]; then
    echo "Drift detected! Fixing..."
    # Act
    kubectl patch cm reconciliation-demo -p '{"data": {"status": "active"}}'
  else
    echo "State consistent."
  fi
  
  sleep 5
done
----

=== Step 3: Triggering a Discrepancy
Open a second terminal and modify the resource manually:
`kubectl patch cm reconciliation-demo -p '{"data": {"status": "broken"}}'`

Watch the first terminal. Within 5 seconds, the "controller" will detect the drift (the current state no longer matching the desired state) and reconcile it back to "active".

== Troubleshooting Guidance
*   **Infinite Requeue Loops:** If your logic fails to reach the desired state, ensure you are not queuing the same item indefinitely without backoff, as this will spike CPU usage.
*   **Eventual Consistency:** Remember that because the Informer cache is updated asynchronously, there may be a slight delay between a change in the API server and the controller's awareness of that change. Always design your system to handle "eventual" rather than "instant" convergence.
