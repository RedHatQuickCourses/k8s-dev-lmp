#  The declarative intent of Kubernetes Resources

= The Declarative Intent of Kubernetes Resources

In traditional systems administration, operators often use **imperative** commands (e.g., "Install this package," "Start this service," "Restart this process"). In Kubernetes, this model is inverted. Kubernetes is fundamentally a **declarative, API-centric configuration management system**.

== The Core Philosophy: Desired vs. Actual State

The "declarative intent" refers to the practice of describing the *goal* (the "what") rather than the *steps* (the "how"). You provide the Kubernetes API with a blueprint—the desired state—and the system works tirelessly to make the actual state match that description.

=== Imperative vs. Declarative

*   **Imperative:** You give a sequence of instructions. If a step fails halfway through, the system is left in an inconsistent, partial state. You must manually account for every possible failure scenario.
*   **Declarative:** You define the final result in a YAML or JSON manifest. If the system crashes, is updated, or is tampered with, the control plane identifies the drift between the current state and the declared state and performs the necessary actions to reconcile them.

== Anatomy of Declarative Intent

Every Kubernetes object relies on a standard structure defined in its manifest. This structure ensures that the API server can process and store your intent effectively.

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec: # <1>
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template: # <2>
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
----
<1> **Spec:** The definitive record of the "Desired State." This is what you, the user, want the system to look like.
<2> **Template:** A blueprint used by controllers to create new resources (like Pods) that conform to your intent.

== How the System Processes Intent

The transition from intent to reality happens through a continuous, asynchronous reconciliation loop:

1.  **Submission:** You submit a resource manifest to the `kube-apiserver`.
2.  **Validation:** The API server ensures the manifest is syntactically and semantically correct (via Admission Webhooks).
3.  **Persistence:** The intent is saved as a structured object in `etcd`.
4.  **Observation:** Controllers (like the Deployment Controller) watch the API server for changes.
5.  **Reconciliation:** The controller compares the current state (e.g., "0 pods are running") with your desired state ("3 pods should be running").
6.  **Action:** The controller issues commands to align reality with your intent.

== Hands-on Activity: Observing Drift and Self-Healing

In this activity, we will demonstrate how Kubernetes enforces your declarative intent despite external interference.

### Prerequisites
*   A running Kubernetes cluster (e.g., Minikube, Kind, or OpenShift).
*   `kubectl` configured and authenticated.

### Step 1: Create the Desired State
Apply a simple deployment manifest to the cluster.

[source,bash]
----
kubectl create deployment nginx-demo --image=nginx --replicas=2
----

### Step 2: Observe the System Action
Check that the deployment has reconciled the desired state.

[source,bash]
----
kubectl get pods -l app=nginx-demo
# You should see 2 pods running.
----

### Step 3: Introduce "Drift" (Imperative Interference)
Manually delete one of the pods. This represents a system failure or accidental deletion.

[source,bash]
----
# Find a pod name
POD_NAME=$(kubectl get pods -l app=nginx-demo -o name | head -n 1)
# Delete it
kubectl delete $POD_NAME
----

### Step 4: Validate Self-Healing
Query the pods again immediately.

[source,bash]
----
kubectl get pods -l app=nginx-demo
----

**Observation:** You will notice that a new pod is being created almost instantly. The Deployment controller observed that the *actual* state (1 pod) no longer matched the *declared* state (2 pods) and automatically rectified the situation. 

*Key Takeaway:* You never told the system to "create a new pod." You told the system to maintain 2 replicas, and the system took ownership of that intent.
