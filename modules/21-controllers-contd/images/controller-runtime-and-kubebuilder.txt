In our previous discussions, we explored how to build controllers by manually wiring up informers, listers, and work queues. The controller-runtime library simplifies this significantly by abstracting that machinery behind a single interface. By implementing a Reconcile method, you allow the framework to handle complex tasks like event filtering, caching, leader election, and worker management. This approach dramatically reduces boilerplate code while maintaining the same level-triggered, eventually-consistent model.

Every controller-runtime controller is built around a Reconciler struct that embeds a client and a scheme. The Reconcile method is the heart of your controller. It receives a request that carries only a NamespacedName, rather than the object itself. To get the current state, you use the client to fetch the object from the cache. This is a critical design choice because it prevents your controller from acting on potentially stale data that might have been passed through an event handler.

When your controller runs inside a cluster, it requires specific RBAC permissions. To manage this, Kubebuilder uses marker comments placed directly above the Reconcile method. When you run the command "make manifests," the controller-gen tool processes these comments to automatically generate the necessary ClusterRole manifests.

Now, let’s discuss how we define what a controller cares about using the Builder pattern. Within the SetupWithManager method, you define the resources the controller tracks. 

First, you use the "For" method to specify the primary resource the controller reconciles. Every time this resource is created, updated, or deleted, a reconciliation request is added to the queue. 

Second, you can use "Owns" to track child resources. If you define a child as owned, changes to that child will automatically trigger a reconciliation of the parent. Furthermore, the framework automatically sets an OwnerReference, which ensures the child resource is cleaned up via garbage collection if the parent is deleted. 

Finally, you can use "Watches" to monitor arbitrary resources that aren't owned by your primary object. This is particularly useful when your controller needs to react to changes in shared resources like ConfigMaps or Secrets.

A quick but important warning: controller-runtime automatically creates informers for any resource type you use in a client get or list operation, even if you haven't explicitly declared them in your For, Owns, or Watches methods. This can lead to performance issues because cache warming can block your worker goroutine. To prevent this, consider setting the "ReaderFailOnMissingInformer" flag to true on your manager; this helps you catch and fix any accidental implicit watches.

Finally, you may be wondering about the relationship between Kubebuilder and the Operator SDK. The Operator SDK actually uses Kubebuilder under the hood for Go-based operators. Because they both use the same controller-runtime library, the generated code is nearly identical. 

However, the Operator SDK adds several high-level features, including integration with the Operator Lifecycle Manager for packaging, tools to publish to OperatorHub, a scorecard tool for validating best practices, and support for building operators using Ansible or Helm. For pure Go operators, the choice between them often comes down to which ecosystem tools you prefer, as the core reconciliation logic and RBAC markers remain the same. 

For further details, I encourage you to consult the official Kubebuilder documentation and the Operator SDK resources available online.
