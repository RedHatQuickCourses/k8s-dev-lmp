In this lesson, we are going to explore Admission Control Webhooks, a critical component for managing security and policy within Kubernetes.

To understand where these fit into the system, consider the Kubernetes request pipeline. Admission control runs after authentication and authorization are complete, but before the object is actually persisted to storage. Think of it as your final line of defense for enforcing policies on write operations, such as creating, updating, or deleting resources. It is important to note that read operations, like "get," "watch," or "list," bypass admission control entirely.

The admission process is divided into two distinct phases. First is the "Mutating admission" phase, where controllers can modify the incoming object, such as injecting default values. Second is the "Validating admission" phase, where controllers evaluate the request to accept or reject it, but they are not permitted to modify the object. If any controller in either phase rejects the request, the entire operation fails immediately and an error is returned to the client. If you would like a refresher on how this fits into the full API request lifecycle, please consult the documentation on that topic.

Kubernetes includes several built-in admission controllers compiled directly into the API server. Some of the most important ones include: 

First, the "NamespaceLifecycle," which ensures that you cannot create objects in namespaces that are terminating or do not exist, and it protects critical namespaces like "default," "kube-system," and "kube-public" from accidental deletion.

Next, the "LimitRanger," which enforces constraints defined in "LimitRange" objects and can apply default resource requests to pods.

The "ServiceAccount" controller, which automates setup for pods by handling token injection and image pull secret references.

The "MutatingAdmissionWebhook" and "ValidatingAdmissionWebhook," which allow you to call external webhooks to handle custom logic. 

And finally, the "ResourceQuota" controller, which enforces aggregate resource consumption limits for each namespace.

If you need to extend this functionality, you can write your own webhook. A webhook is essentially an HTTPS server that exposes an endpoint to accept an "AdmissionReview" request and return a corresponding response. The API server sends a JSON payload describing the operation, and your webhook must return an allowed status of either true or false.

You register a webhook by creating a "ValidatingWebhookConfiguration" or "MutatingWebhookConfiguration" resource. When configuring these, there are three key fields to keep in mind:

First, "rules," which define which API groups, versions, resources, and operations trigger the webhook.

Second, "clientConfig," which specifies how the API server reaches your webhook, whether through an in-cluster service or an external URL, along with the CA bundle for TLS verification.

Third, "failurePolicy," which controls behavior when the webhook is unreachable. You can choose to "Fail" the request or "Ignore" it and let the request proceed.

For example, when creating a validation webhook for pods, you define the API group and version, specify that it applies only to "CREATE" operations, and point the configuration to your specific validation service.

For developers, the OpenShift "generic-admission-server" library is a great resource. It simplifies development by reusing the core Kubernetes infrastructure for things like TLS, authentication, and authorization.

Before you begin building, keep these important points in mind: Webhook chaining can have complex ordering implications. Because mutating webhooks may run multiple times, the order between multiple webhooks of the same type is not guaranteed. For that reason, you should always set your "failurePolicy" to "Fail" in production environments. This ensures that you don't silently skip validation if one of your webhooks becomes unreachable.
