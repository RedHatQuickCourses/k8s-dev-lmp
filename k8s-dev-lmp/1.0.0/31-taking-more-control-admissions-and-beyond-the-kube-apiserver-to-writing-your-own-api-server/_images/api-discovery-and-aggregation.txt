Before a client can successfully interact with the Kubernetes API, it must first understand which resources are available and which operations are supported. This process is handled by the discovery API.

Every Kubernetes cluster publishes its discovery information through several well-known endpoints. The slash "api" endpoint lists core resources like Pods, Services, and ConfigMaps. The slash "apis" endpoint lists all named API groups, such as batch, apps, or networking. Finally, specific endpoints formatted as slash "apis," slash "group," slash "version" describe the resources available within that specific version, including supported verbs, resource scope, and subresources.

For each resource, the discovery response provides essential details such as the resource name, whether it is namespaced, the supported verbs like get or delete, and the group-version-kind. Furthermore, OpenAPI schema documents are available at slash "openapi/v2" and "v3," providing full structural definitions for every resource type. Keep in mind that OpenAPI version 3 is the preferred format, as it offers a lossless representation of the API schema.

Now, let's discuss a common performance challenge known as the "discovery storm." In traditional, unaggregated discovery, a client must make one HTTP request for every single API group version to build a complete map of the cluster. In a production environment with many Custom Resource Definitions, or CRDs, a cluster can easily contain eighty or more group versions. This forces a client like kubectl to perform a massive burst of requests during initialization. On large clusters, this creates significant performance issues and potential throttling.

To solve this, Kubernetes introduced Aggregated Discovery, which has been stable since version 1.30. This approach collapses all discovery information into just two requests—one for the core API and one for the named groups. By using content negotiation, a client can request this aggregated format by providing a specific Accept header: "application/json," with parameters specifying the API discovery version and the APIGroupDiscoveryList type. The server then returns all group, version, and resource information in one response. Even better, this system uses ETag headers for efficient cache validation, allowing the server to return a 304 "Not Modified" response if the data hasn't changed. Clients using "client-go" version 1.26 or later will automatically take advantage of this feature when the server supports it, with a transparent fallback for older clusters.

Finally, it is important to understand the difference between Custom Resource Definitions, or CRDs, and aggregated API servers when extending Kubernetes. CRDs are the standard, declarative approach that requires no coding; they use the existing etcd storage and are validated through OpenAPI schemas. Conversely, an aggregated API server requires you to build and deploy a custom Go binary, but it allows for custom storage backends, arbitrary validation logic, and support for custom subresources or protocol buffers.

An important point to remember is that for the vast majority of use cases, CRDs are the right choice. You should only consider an aggregated API server if you have specific requirements, such as using a non-etcd storage backend, implementing complex subresources, or needing support for protocol buffers.

For more information, you can consult the official Kubernetes API documentation, the enhancement proposal for Aggregated Discovery, or the documentation on Custom Resources.
