Implementing custom API servers

Implementing Custom API Servers

When the standard Custom Resource Definition (CRD) mechanism is insufficient for your needs, the Kubernetes API Aggregation Layer provides the extensibility required to introduce your own, fully functional API server into a Kubernetes cluster.

Why Build a Custom API Server?

While CRDs are the standard for most extensions, you might need a dedicated API server when: * Complex Data Models: Your API requires complex logic, non-standard storage, or non-Kubernetes-native structures that do not map well to the CRD schema. * Custom Storage: You need to store data in a system other than etcd (e.g., a SQL database or an external cloud service). * Advanced API Semantics: You require custom proxying, specialized conversion logic, or complex resource relationships that the standard CRD lifecycle cannot support. * Independent Scalability: You want to scale your API’s control plane independently of the primary Kubernetes API server.

The API Aggregation Layer

The API Aggregation Layer allows you to "plug in" your own API server alongside the core Kubernetes API server. It uses an APIService object to register your server, which acts as a proxy:

  1. A client sends a request to the main kube-apiserver.

  2. The kube-apiserver recognizes that the URL path belongs to your registered APIService.

  3. The kube-apiserver proxies the request to your custom server.

Hands-on Activity: Exploring API Discovery

Before building, it is essential to understand how the system discovers these aggregated APIs. You can query the discovery endpoint to see how aggregated APIs are exposed.

Ensure you have access to a running cluster and have oc or kubectl configured.

Step 1: Accessing the Discovery Endpoint

Use the oc proxy to securely reach the API server and request the APIGroupDiscoveryList to see how the system registers and groups APIs.

# Start the proxy in the background or a separate terminal
oc proxy &

# Query the discovery endpoint
curl -v http://127.0.0.1:8001/api \
  -H "Accept: application/json;v=v2;g=apidiscovery.k8s.io;as=APIGroupDiscoveryList"

Step 2: Reviewing Implementation Patterns

To understand how to structure your server, examine existing implementations. The sample-apiserver provides the scaffolding for a compliant implementation using k8s.io/apiserver.

  1. Review the Sample: Clone the repository to see the boilerplate code: https://github.com/kubernetes/sample-apiserver

  2. Examine Real-World Case Studies: The OLM (Operator Lifecycle Manager) package manager API server is a production-grade example of a custom API server.

    • Explore the code here: https://github.com/openshift/operator-framework-olm/tree/main/cmd/package-server-manager

Best Practices for Custom API Servers

  • Reusability: Utilize the k8s.io/apiserver library. It handles the heavy lifting of authentication, authorization, and audit logging, ensuring your custom server behaves like a native Kubernetes component.

  • Compatibility: Always ensure your server supports the standard Kubernetes REST patterns. If you deviate from these, tools like kubectl or oc may not interact with your resources correctly.

  • Security: Because your API server will be part of the trusted control plane, treat its development with the same rigor as the core Kubernetes components. Implement proper RBAC and transport security (TLS).

  • Discovery: Implement the APIGroupDiscovery interface correctly to ensure your resources are visible to discovery clients and UI tools.
