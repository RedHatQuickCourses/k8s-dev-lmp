Admission control webhooks (Validating and Mutating)

Admission Control Webhooks: Validating and Mutating

In the Kubernetes request lifecycle, the kube-apiserver acts as the gatekeeper. Before an object is persisted to etcd, it passes through a sequence of admission controllers. While many are built-in (compiled into the binary), Admission Webhooks allow you to extend this functionality dynamically by calling out to external HTTP services.

Understanding Admission Controllers

Admission controllers are plugins that intercept requests to the Kubernetes API server after authentication and authorization are successful, but before the object is stored.

There are two primary types of webhooks:

  1. Mutating Admission Webhooks: These modify the request object before it is persisted. They are processed first. A classic example is injecting a "sidecar" container or adding default labels to a Pod.

  2. Validating Admission Webhooks: These validate the request object against defined policies. If the object violates a policy, the request is rejected with an error. They are processed after mutation, ensuring they see the final version of the object.

Order matters. Mutating webhooks are executed before validating ones to ensure that the validation logic acts upon the final, intended state of the object.

The Webhook Lifecycle

When a request (e.g., kubectl apply) hits the API server, the following flow occurs:

  1. Object Conversion: The API server converts the object into an internal version.

  2. Mutation: The kube-apiserver sends an AdmissionReview request to registered Mutating Webhooks. The webhooks return an AdmissionResponse containing a JSON Patch to modify the object.

  3. Object Schema Validation: Built-in validation checks occur.

  4. Validation: The kube-apiserver sends an AdmissionReview request to registered Validating Webhooks. The webhooks return an AdmissionResponse with allowed: true or allowed: false.

  5. Persistence: If all checks pass, the object is saved to etcd.

Webhooks vs. Policy Engines

While you can write custom webhooks for specific logic, complex cluster governance is often better handled by dedicated Policy Engines like OPA Gatekeeper or Kyverno.

  • Custom Webhooks: Best for highly specific, procedural logic that requires deep integration with your internal systems (e.g., calling a legacy database or a proprietary container registry service).

  • Policy Engines: Best for declarative governance (e.g., "All Pods must have a cost-center label"). They provide a high-level DSL (Domain Specific Language) that is easier to audit and manage at scale compared to writing and maintaining custom Go binaries.

Hands-on Exercise: Implementing a Registry Validator

In this exercise, you will create a Validating Webhook that prevents users from deploying container images from unauthorized registries.

Prerequisites

  • A running Kubernetes cluster (or kind).

  • cert-manager installed (to handle the HTTPS certificates required by the API server).

  • A Go development environment.

Step 1: Define the ValidatingWebhookConfiguration

This object tells the kube-apiserver which resources to watch and where to send the requests.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: registry-validator
webhooks:
  - name: validate.registry.example.com
    rules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
    clientConfig:
      service:
        name: registry-validator-svc
        namespace: default
        path: "/validate"
    admissionReviewVersions: ["v1"]
    sideEffects: None

Step 2: Implement the Webhook Server

Your binary must expose an HTTP endpoint that consumes admission.k8s.io/v1 AdmissionReview objects and returns a JSON response.

// Simplified logic for the /validate endpoint

Step 3: Verification

After deploying your server and the ValidatingWebhookConfiguration:

  1. Attempt to create a Deployment using an image from docker.io (if unauthorized).

  2. Observe the API server rejecting the request: Error from server: admission webhook "validate.registry.example.com" denied the request: Unauthorized Registry

Always ensure your webhook server is highly available. If the webhook is unreachable, the API server will either "Fail Open" or "Fail Closed" based on the failurePolicy field in your configuration. For security, failurePolicy: Fail is recommended.
