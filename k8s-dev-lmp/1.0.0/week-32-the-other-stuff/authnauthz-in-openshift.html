AuthN/AuthZ in OpenShift

AuthN/AuthZ in OpenShift

In the context of the Kubernetes developer learning path, moving from vanilla Kubernetes to OpenShift introduces a more integrated, opinionated approach to Authentication (AuthN) and Authorization (AuthZ). While OpenShift is built on top of Kubernetes, it extends the core primitives to provide a robust, enterprise-grade identity management system.

Authentication (AuthN) in OpenShift

In vanilla Kubernetes, AuthN is often handled via static tokens, certificates, or OIDC providers. OpenShift introduces the OAuth Server, a built-in identity provider layer that simplifies the management of users and access tokens.

The OAuth Server

The OpenShift OAuth server manages authentication requests. Unlike Kubernetes, where you might have to manage kubeconfig files with embedded tokens, OpenShift users typically log in via a web console or oc login, which exchanges credentials for an OAuth access token.

  • Identity Providers (IDPs): OpenShift allows you to integrate with external systems such as LDAP, GitHub, GitLab, Google, or OIDC.

  • User and Identity Objects: OpenShift separates the concept of an Identity (the external user record) from the User (the internal representation of that user within the cluster).

Authorization (AuthZ) in OpenShift

OpenShift builds upon Kubernetes Role-Based Access Control (RBAC) but adds a critical layer of abstraction known as Security Context Constraints (SCCs).

RBAC vs. SCCs

While RBAC governs who can perform actions on API objects (like get, list, create), SCCs govern what a Pod is allowed to do from a security perspective (e.g., can it run as root, can it access the host network, can it mount host volumes).

Security Context Constraints (SCCs)

SCCs define the set of conditions that a pod must run with to be accepted by the system. * Pre-defined SCCs: OpenShift comes with default SCCs (e.g., privileged, anyuid, restricted-v2). * The SCC Admission Controller: When a pod is submitted, the SCC admission controller evaluates the service account under which the pod is running and checks it against the available SCCs. If the pod violates the security constraints, the request is rejected.

Hands-on Activity: Inspecting SCCs and Roles

This activity demonstrates how to view the security permissions assigned to your service account.

  1. List available Security Context Constraints:

    oc get scc

  2. Inspect a specific SCC to understand its constraints:

    oc describe scc restricted-v2

  3. Check which service accounts can use a specific SCC:

    You will notice the users and groups fields. These fields define which entities are permitted to request this security context.

  4. View RoleBindings for your current project:

    oc get rolebindings

    • Observation: Notice the difference between RoleBinding (namespace-scoped) and ClusterRoleBinding (cluster-scoped).

Key Concepts Summary

Concept

Description

OAuth Server

Centralized identity management for cluster access.

User/Identity

Mapping external auth providers to internal cluster objects.

RBAC

API-level access control (Verb + Resource).

SCC

Pod-level security constraints (Privileged mode, SELinux, UIDs).

When building controllers in OpenShift, ensure your ServiceAccount has the necessary RoleBindings and, if your pod requires specific privileges (like host access), ensure your project’s ServiceAccount has been granted access to the appropriate SCC using oc adm policy add-scc-to-user.
