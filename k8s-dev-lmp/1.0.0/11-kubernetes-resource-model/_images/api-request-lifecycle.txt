Every interaction with a Kubernetes cluster, whether it originates from kubectl, an internal controller, or an external operator, must pass through the Kubernetes API server’s request pipeline. Understanding these stages is essential for building secure, efficient, and extension-ready applications.

When a request enters the API server, it does not immediately interact with etcd. Instead, it traverses a specific chain of stages, each responsible for a distinct concern. For a mutation request, these stages execute in a set order.

First is authentication. This stage validates the caller's identity using X.509 client certificates, bearer tokens, or OIDC tokens. If authentication fails, the request is immediately rejected with a 401 Unauthorized response.

Second is the audit stage, which records the request for compliance and debugging. Every request is logged, providing a full trail of who performed an action and when it occurred.

Third is impersonation, which allows authenticated users to act as another user or group. The server verifies that the caller has the authority to impersonate the target identity before proceeding.

Fourth is priority and fairness. This stage classifies requests into flow schemas and priority levels to prevent the API server from becoming overloaded. By categorizing requests—such as distinguishing between leader election and background listing—the server applies rate-limiting to ensure cluster stability. It is important to remember that this mechanism is how the server prevents a misbehaving controller from starving other clients. Without it, a single controller flooding the system with list calls could degrade responsiveness for the entire cluster.

Fifth is authorization, which checks whether the authenticated identity is allowed to perform the requested action on the specified resource. Kubernetes supports several authorization modes, including RBAC, Node, Webhook, and ABAC.

Sixth is the mutation stage. Here, mutating admission webhooks can modify the request object before it is validated. This is the stage where sidecars are injected, default values are set by policy engines, and labels are added automatically.

Seventh is validation. Both schema validation and validating admission webhooks ensure the object meets all constraints. Unlike mutating webhooks, validating webhooks cannot change the object; they can only accept or reject it.

Finally, the eighth stage is storage. The validated object is serialized and persisted to etcd. At this point, the desired state is durably recorded and available for controllers to act on.

Before we move on, keep in mind that a vulnerability in HTTP/2 known as the "rapid reset" attack led the client-go library to default to HTTP/1.1 connections. This is a helpful detail to recall when debugging connection behavior between your clients and the API server.

Now, let's look at how to explore the API. The API server exposes discovery endpoints that let you inspect available API groups, versions, and resource types. This is a great way to verify that your requests are reaching the server and to understand the API structure.

To begin, you can start a local proxy to the API server by running the command `kubectl proxy --port=8001`. 

Once the proxy is running, you can use standard tools to interact with the API. For example, to list all API groups, use the curl command to query the localhost port and pipe the output to jq. To get an aggregated discovery document in version two format, you can query the API endpoint with the appropriate accept header. Additionally, you can inspect a specific resource type, such as pods in the default namespace, by querying the pod endpoint.

These commands confirm that your request successfully passes through the authentication and authorization stages. Furthermore, these discovery endpoints are exactly what client libraries, such as client-go, use under the hood to negotiate API versions and resource schemas.
