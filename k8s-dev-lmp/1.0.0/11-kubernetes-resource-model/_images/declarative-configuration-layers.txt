Declarative configuration management tools allow you to define the desired state of a system. The tool then automatically compares that desired state to reality and updates the managed system to match. To understand how these tools are structured, and why Kubernetes makes its specific architectural choices, it is helpful to look at the three-layer model.

Every declarative configuration management system can be broken down into three distinct layers: the resource schema, the concrete resource syntax, and the convergence engine.

Let’s start with the first layer: the resource schema. This defines which types of resources the tool can manage and the properties they possess. For example, Puppet uses types like file and mount, while Terraform uses types like aws_instance. Kubernetes features a very explicit resource schema, publishing its core types as a protocol buffer definition. Custom resource types can also provide an OpenAPI v3 validation schema to document and enforce their shape, and Custom Resource Definitions—or CRDs—extend this schema dynamically.

The second layer is the concrete resource syntax. While the schema tells us what resources exist, we need a concrete syntax to express specific instances. This is what you type into an editor, check into version control, and pass to the tool. Many systems use a custom language to handle this, which provides helpful abstractions like modules, variables, and loops. However, this often leads to the ad-hoc growth of complex language features over time. Kubernetes takes a different approach: it only accepts raw JSON or YAML. The work of abstraction—such as parameterization or iteration—is pushed entirely to external tools like Helm, Kustomize, or Jsonnet.

The third layer is the convergence engine. Its job is to take a concrete resource catalog and update the managed system to match it. The configuration specifies the desired state, and the engine determines how to achieve it. In Kubernetes, this is handled by controllers. Each controller watches a specific set of resource types and continuously reconciles the observed state with the desired state.

This strict separation of layers has several benefits. First is testability. Because you can generate your configuration separately from the convergence process, you can write tests to make assertions about your catalog without needing to touch a live cluster. This allows CI pipelines to catch unintended changes before they reach production.

Second is confidence in refactoring. As long as your configuration tooling produces the same final resource catalog, you can be certain that your changes will not have a negative functional effect on the cluster.

Third is the separation of concerns. Kubernetes focuses on the resource schema and convergence, while users are free to choose the abstraction tool that best fits their specific needs. By not embedding abstraction into its core, Kubernetes keeps its API surface simple and allows developers to use familiar programming styles.

To summarize how these layers differ across platforms, consider this comparison:

Puppet and Chef use a custom domain-specific language that conflates resource definition with abstraction, using a built-in agent to apply catalogs to hosts. Terraform uses HashiCorp Configuration Language, or HCL, which is tightly coupled to the resource schema and uses a built-in plan and apply engine to manage state. Kubernetes, by contrast, relies solely on raw JSON or YAML for its input, offloads abstraction to external tools, and uses decoupled, per-resource-type controllers to perform the work of convergence.

Ultimately, Kubernetes achieves the purest separation of these three layers. By keeping abstraction outside of its core, it provides a stable foundation for infrastructure management.
