At its core, Kubernetes is an API-centric, declarative configuration management and container orchestration system. Rather than issuing imperative commands to tell the server what to do, you interact with the system by declaring the desired state of your resources as pure data.

The heart of the control plane is the API server. This server acts as a central coordination point and persists your desired state into a key-value store called etcd. To make reality match those declarations, Kubernetes relies on an ecosystem of asynchronous controllers. These controllers continuously watch the API server for changes; they compare the current observed state of the world to your desired state and actively reconcile any differences. This separation of responsibilities—where the API server maintains shared state and independent controllers actuate it—is the same fundamental architecture you will use and extend when building your own custom operators.

To better understand how this works, it helps to think of any declarative configuration management system, including Kubernetes, as being composed of three distinct layers.

The first layer is the Resource Schema. This is the definition of which types of resources exist and what shape they take. In Kubernetes, this is expressed through API group-version-kind definitions, Protocol Buffer schemas for built-in types, and OpenAPI v3 validation schemas for custom resources.

The second layer is the Concrete Resource Syntax. This represents the raw YAML or JSON data that you, as the user, author and submit to the API server. Keep in mind that Kubernetes deliberately accepts only fully-realized resource definitions. It pushes abstraction—such as templating and parameterization—to external tools like Helm, Kustomize, or general-purpose programming languages.

The third and final layer is the Convergence Engine. This consists of the controllers that take a concrete set of resource declarations and actuate the managed system to match them. Kubernetes has perhaps the most explicit notion of this layer of any declarative system, as it is directly embodied in the controller architecture.

This layered model clarifies why Kubernetes separates its concerns the way it does. The API server owns the schema and the storage of declared state, while the controllers independently implement the logic to make reality converge.
