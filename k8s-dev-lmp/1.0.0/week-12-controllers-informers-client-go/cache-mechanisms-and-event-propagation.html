Cache mechanisms and event propagation

Cache Mechanisms and Event Propagation

In Kubernetes, controllers do not query the kube-apiserver for every single operation. Doing so would overwhelm the API server and introduce significant latency. Instead, client-go provides a robust caching and synchronization mechanism that allows controllers to operate on a local, near-real-time replica of the cluster state.

The Role of Local Caching

The primary goal of a cache in client-go is to decouple the controller’s logic from the API server’s throughput. By maintaining a local copy of objects, the controller can: * Reduce API Load: Read operations (List/Get) are served from memory, not the network. * Improve Performance: Local lookups via Listers are significantly faster than HTTP requests. * Handle Disconnects: If the network to the kube-apiserver flickers, the controller can continue processing its current queue state.

Event Propagation: From etcd to Controller

Event propagation is the pipeline that ensures the local cache remains synchronized with the ground truth in etcd.

@startuml
skinparam componentStyle uml2
[etcd] -> [kube-apiserver] : Watch Event
[kube-apiserver] -> [Reflector] : HTTP/Watch
[Reflector] -> [DeltaFIFO] : Add/Update/Delete
[DeltaFIFO] -> [Indexer] : Update Cache
[Indexer] -> [Informer] : Notify Event Handler
@enduml

1. The Reflector

The Reflector is the foundation. It performs a List and Watch operation on a specific resource type. It populates the initial state and then watches for subsequent changes (ADD, UPDATE, DELETE). These changes are pushed into the DeltaFIFO queue.

2. DeltaFIFO: The Buffer

The DeltaFIFO is a queue that stores the changes (deltas) received from the Reflector. * Crucial Note: Queues in Kubernetes are strictly FIFO (First-In, First-Out). * It ensures that even if events arrive in rapid succession, the controller processes them in the order they occurred.

3. The Indexer (Local Store)

The Indexer is the component that holds the actual state. It acts as the local database for the controller. When an item is pulled from the DeltaFIFO, the Indexer is updated to reflect the new state, ensuring that the controller’s Lister has access to the most recent object version.

4. Informer Event Handlers

Once the cache is updated, the Informer triggers user-defined event handlers (AddFunc, UpdateFunc, DeleteFunc). These handlers typically do not perform business logic directly; instead, they add the key (namespace/name) of the object to a WorkQueue.

Practical Exercise: Inspecting Cache Synchronization

In this exercise, you will observe how the cache handles an event.

Steps

  1. Initialize an Informer: Using client-go, create a SharedInformerFactory for Pods. [source,go] ---- factory := informers.NewSharedInformerFactory(clientset, time.Second*30) podInformer := factory.Core().V1().Pods().Informer() ----

  2. Add Event Handlers: Log the events to see the propagation in action. [source,go] ---- podInformer.AddEventHandler(cache.ResourceEventHandlerFuncs{ AddFunc: func(obj interface{}) { pod := obj.(*corev1.Pod) fmt.Printf("Cache Updated: Pod %s added\n", pod.Name) }, }) ----

  3. Start the Informer: Run the informer in a background goroutine. [source,go] ---- stopCh := make(chan struct{}) defer close(stopCh) factory.Start(stopCh) cache.WaitForCacheSync(stopCh, podInformer.HasSynced) ----

  4. Observe: Create a Pod in your cluster using kubectl run. Watch your application logs to see the AddFunc trigger immediately after the cache syncs the event.

Key Takeaways

  • Informers are your "eyes" on the cluster.

  • Listers are your read-only view of the local cache.

  • WorkQueues are your buffers for processing items asynchronously.

  • Always use FIFO: Never attempt to reorder events; consistency is maintained by processing the stream of changes in the order they were emitted by the API server.
