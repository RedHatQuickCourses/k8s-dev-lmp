Welcome to this session on the architecture of client-go.

client-go is the official Go client library for the Kubernetes API server. It provides the essential event-driven programming primitives that every controller and operator is built upon. In fact, even the command-line tool, kubectl, uses client-go under the hood. If you are planning to build your own Kubernetes controller, this is the library you need to understand.

Conceptually, there are three layers that sit between a developer and the API server. First, at the bottom, is the API server itself, which serves as the source of truth for cluster state. Second, we have client-go, which provides the typed clients, informers, listers, caches, and workqueues. Third, sitting on top, is controller-runtime. This is a higher-level framework that masks many of the complex, event-oriented architecture details found in client-go.

The key packages within client-go include tools/cache, which handles informers and caches; the kubernetes package for typed clientsets; the dynamic package for untyped clients; and the discovery package for API group discovery.

Let’s look at the core components found within the tools/cache package.

Every client-go based controller relies on the Reflector. The Reflector mirrors the API server’s state into a local store using a process called ListAndWatch. Upon startup, it performs an initial list to fetch all existing objects and records the current resource version. It then opens a long-running watch connection starting from that version to receive incremental updates. When a change is detected, the Reflector places the object, along with the type of change, into a DeltaFIFO queue.

DeltaFIFO is a producer-consumer queue that stores resource events as incremental deltas. The Reflector acts as the producer, while the Informer's process loop acts as the consumer. DeltaFIFO is critical for controller correctness because it provides two key guarantees. First, it ensures exactly-once, in-order processing for each resource. Second, it performs deduplication; if multiple updates for the same key arrive before the consumer processes them, the queue coalesces those updates so the consumer only sees the latest state.

Next, we have the Indexer. The Indexer is a thread-safe local cache that stores objects popped from the DeltaFIFO. It uses a default key function to generate keys formatted as namespace/name. 

I must share an important warning here: multiple controllers within the same process share the Indexer cache. Because of this, you should never mutate a cached object directly. Even changing a shallow field like annotations without a deep copy can corrupt the object for every other controller that reads it. Always use the API scheme copy or the generated DeepCopy method before modifying a cached object.

Additionally, keep in mind that each resource stored in etcd has a hard size limit of approximately one point five megabytes. You should consider this limit when designing custom resources that might have large specs or status fields.

To manage resources efficiently, client-go uses the SharedInformerFactory. This component multiplexes watchers across controllers so that only one API server connection is maintained per resource type within a process. This approach significantly saves on API connections, reduces serialization and deserialization costs, and minimizes server-side memory usage. 

The SharedInformer interface defines the contract for these informers. By using the AddEventHandler method, you can register your controller’s callbacks. Once you call the Run method, the informer starts the Reflector and begins populating the cache.

Now, let’s visualize the data flow pipeline. Data moves from the API server through the Reflector, which enqueues deltas into the DeltaFIFO. From there, the Informer pops the data and stores it in the Indexer cache, which then invokes your registered event handlers. Your event handlers typically enqueue a namespace/name key into a workqueue. Finally, your controller's sync handler dequeues that key to execute your specific reconciliation logic. 

It is important to note that the top half of this pipeline—the Reflector, DeltaFIFO, and Indexer—is managed entirely by client-go. The bottom half, which includes your event handlers, workqueue, and sync logic, is the code you will write as a controller author.

For further learning, you can consult the official Kubernetes documentation or the referenced online resources, which provide deeper technical walkthroughs and presentations on how these components function under the hood.
