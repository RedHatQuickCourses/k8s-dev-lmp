Informer patterns are elegant when working with small clusters, but they introduce subtle failure modes as you scale. This lesson covers the most common pitfalls, based on official Kubernetes controller guidelines and production experience in large-scale environments.

Let’s start with the most important principle for writing correct controllers: Informers are level-driven, not edge-driven.

A level-driven controller examines the current state of the world to determine what action to take. An edge-driven controller, on the other hand, reacts to the delta—or the transition—between an old state and a new state.

It is a critical warning that you should never compare the old object and the new object in your UpdateFunc handler to decide whether to reconcile. The old object parameter is essentially a trap; it encourages edge-driven logic that will fail whenever events are missed, reordered, or coalesced. 

Edge-driven logic is flawed because Informers do not guarantee you will see every intermediate state; they only guarantee you will eventually see the current state. During periods of high churn, multiple updates may be merged into one event. Furthermore, if your controller restarts, it receives the full current state via an initial list, meaning there is no previous state to compare against. The correct approach is to enqueue the object's key unconditionally in your UpdateFunc, then have your sync handler read the actual current state from the cache and reconcile from there.

Next, let's look at scaling pitfalls. These issues typically emerge when running clusters with tens of thousands of resources.

First is the initial list phase. When an Informer starts, it performs a full list operation. If you have one hundred thousand pods, it loads all of them into memory simultaneously, triggering an AddFunc for every single one.

Second is serial handler execution. Event handlers run serially on an unbounded ring buffer. If your handler performs a slow operation, like a database write or a network call, events will queue up in memory while waiting for their turn.

These two factors can combine into a dangerous "out of memory" loop. The initial list returns a massive volume of objects, and if the handler is slow, the backlog grows. Meanwhile, the watch stream continues to generate new events, and periodic resyncs re-deliver cached objects. Memory usage climbs until the process is killed, the pod restarts, and the cycle repeats.

To mitigate these risks, always use a workqueue. This is the primary recommendation in official guidelines; it moves processing out of the event handler into a rate-limited queue that supports retries and backoff. Additionally, use label selectors with your informer factory to restrict the data you watch, and use the SetTransform hook to strip out unnecessary fields, which significantly reduces your memory footprint.

Regarding error handling, never silently swallow errors inside your sync handler. If you return an error, your work loop can handle it properly. Specifically, returning an error triggers the workqueue to use rate-limited requeueing, which employs an exponential backoff strategy to prevent hammering your system.

When managing the workqueue, there are three key operations to remember. First, use Done to release the processing lock; this must always be called, typically via a defer statement. Second, use Forget upon successful completion to reset the backoff counter. Finally, use AddRateLimited upon failure to ensure the item is retried after an increasing delay.

Finally, let's address some common mistakes observed during code reviews. 

Always perform a deep copy before mutating objects retrieved from the cache. The Informer cache is shared, and modifying it directly will corrupt the data for every other controller in your process. 

Also, ensure you wait for cache synchronization. Starting to process items before the cache has synced can lead to incorrect decisions, such as a controller thinking no resources exist when they simply haven't loaded yet.

Finally, always use the Lister for reads and the clientset for writes. The Lister is fast because it reads from your local cache without network overhead, while the clientset is necessary for writes and interacts directly with the API server. Furthermore, because the cache is eventually consistent, always re-get a resource from the API server before performing a write operation to ensure you have the latest resource version and avoid conflict errors.
