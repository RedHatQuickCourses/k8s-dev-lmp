Pod scheduling, de-scheduling, and auto-scaling

Week 4.1: Pod Scheduling, De-scheduling, and Auto-scaling

The kube-scheduler is the "matchmaker" of the Kubernetes control plane. It observes newly created Pods that have no assigned node and selects an optimal node for them to run on. This module explores how the scheduler makes these decisions, how pods are evicted or moved, and how Kubernetes automatically adjusts capacity.

The Scheduling Lifecycle

Scheduling is not a single action but a multi-stage pipeline. When a Pod is created:

  1. Filtering (Predicates): The scheduler filters the list of all nodes to find those that meet the Pod’s requirements (e.g., CPU/Memory requests, node selectors, taints/tolerations).

  2. Scoring (Priorities): The scheduler ranks the filtered nodes based on a set of scoring functions (e.g., spreading pods across zones, balancing load).

  3. Binding: The scheduler creates a Binding object in the API server to associate the Pod with the chosen node.

De-scheduling and Eviction

Sometimes, the initial placement of a Pod becomes suboptimal due to cluster changes. This is where De-scheduling and Eviction come into play.

  • Eviction: An API-initiated action where the control plane signals a Pod to terminate (often used during node draining for maintenance).

  • The Descheduler: Because the kube-scheduler only acts when a Pod is created, it does not move Pods once they are running. The Kubernetes Descheduler is an add-on that analyzes cluster state and evicts Pods that violate policies (e.g., too many Pods on one node, or nodes that are significantly under/over-utilized).

Auto-scaling Mechanisms

Auto-scaling ensures that your infrastructure matches your demand. It operates at two levels:

  • Horizontal Pod Autoscaler (HPA): Adjusts the number of Pod replicas based on observed CPU utilization or custom metrics.

  • Vertical Pod Autoscaler (VPA): Adjusts the resource requests and limits of containers in a Pod to ensure they have exactly the right amount of resources.

  • Cluster Autoscaler (CA): Adjusts the number of nodes in the cluster. When the scheduler cannot find a node for a pending Pod, the CA provisions a new node from the underlying infrastructure provider (AWS, GCP, Azure, etc.).

Hands-on Activity: Configuring Pod Affinity and HPA

In this exercise, you will observe how the scheduler respects placement constraints and how HPA reacts to load.

Step 1: Deploy a constrained Pod

Create a YAML file constrained-pod.yaml to ensure your Pod lands on a specific node type.

apiVersion: v1
kind: Pod
metadata:
  name: affinity-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - us-east-1a
  containers:
  - name: nginx
    image: nginx

Step 2: Implement Horizontal Pod Autoscaler

Create an HPA that scales a deployment based on CPU usage.

kubectl autoscale deployment my-app --cpu-percent=50 --min=1 --max=10

Step 3: Verification

  1. Verify the Pod placement: kubectl get pod affinity-pod -o wide.

  2. Check the HPA status: kubectl get hpa.

  3. Troubleshooting Tip: If a Pod remains in Pending state, use kubectl describe pod <pod-name> to view the Events section. The scheduler will explicitly state why a node was rejected (e.g., "0/3 nodes are available: 3 node(s) didn’t match node selector").

Best Practices

  • Always set Requests and Limits: The scheduler relies on these to make capacity decisions. If you don’t set them, the scheduler cannot accurately predict resource contention.

  • Use Pod Disruption Budgets (PDBs): If you are running critical workloads, define a PDB to ensure that during voluntary disruptions (like node upgrades), a minimum number of replicas remain available.

  • Avoid Over-committing: While Kubernetes allows you to over-commit resources, be aware that the kube-scheduler doesn’t know the actual real-time load; it only knows the requested values.
