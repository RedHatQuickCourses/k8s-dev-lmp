When managing Kubernetes workloads, understanding how to define and monitor resource usage is essential. Every container in a Pod can declare two distinct resource values: a request and a limit.

It is important to understand the difference between these two. A request tells the kube-scheduler how much capacity to reserve. The scheduler adds up the requests of all containers in a Pod and only places it on a node that has enough unallocated resources. Requests are strictly a scheduling-time concept and do not constrain the container once it is running. 

In contrast, limits tell the kubelet and the Linux kernel how much a container is allowed to consume at runtime. A container can burst above its request when spare capacity exists, but it cannot exceed its defined limit. Keep in mind that if you set a limit without a request, Kubernetes automatically copies the limit value into the request.

Let’s look at how CPU and memory are handled specifically. CPU is measured in millicores, represented by the symbol "m." One full core is equal to 1000m, so 0.5 cores would be 500m. CPU limits are enforced through a mechanism called CFS throttling. When a container reaches its CPU limit, the kernel restricts its processing time for the remainder of the scheduling interval. Importantly, the container is not killed; it simply runs more slowly. Because this throttling is invisible to many monitoring tools, a sluggish application with low reported CPU usage is a classic sign that your CPU limit may be set too low.

Memory, on the other hand, is measured in bytes, typically using suffixes like Mi for mebibytes or Gi for gibibytes. Unlike CPU throttling, memory limits are enforced by the kernel's Out-Of-Memory killer. If a container tries to allocate more memory than its limit allows while the system is under pressure, the kernel will terminate it. An OOM kill is destructive, meaning the container will restart according to its restart policy, and any in-flight work will be lost.

The scheduler uses these values to find a node with enough available space. Once the Pod is running, the kernel enforces the limits of 500 millicores and 128 mebibytes.

Kubernetes also assigns each Pod a Quality of Service, or QoS class, based on your resource declarations. This class determines the eviction priority if a node runs out of resources. There are three levels:
First, the "Guaranteed" class occurs when every container has requests equal to its limits for both CPU and memory; these Pods are the last to be evicted.
Second, the "Burstable" class applies when at least one container has a request or limit, but they are not all equal; these are evicted after BestEffort Pods.
Finally, "BestEffort" is assigned when no container sets any request or limit; these are the first to be evicted. 
A useful tip for production workloads is to set requests equal to limits, which gives your pods "Guaranteed" status and protects them from eviction during memory pressure.

To maintain cluster stability, administrators can use two tools for namespace-level guardrails. 
A "LimitRange" sets default requests and limits for containers that don't specify them, and it defines minimum and maximum boundaries to prevent unreasonable resource requests. 
A "ResourceQuota" caps the total amount of CPU, memory, and objects a namespace can consume. If a quota is hit, new Pods will fail to create until resources are freed. 

When you run into issues, here are a few practical debugging tips:
If a Pod is stuck in a "Pending" state with a "FailedScheduling" event, it usually means the requests exceed available node capacity. You can verify this by running "kubectl describe node" and comparing the allocatable resources against the allocated ones.
If you see a container restarting with an "OOMKilled" exit reason, it needs a higher memory limit or an investigation into potential memory leaks.
And finally, if you notice high CPU throttling metrics in your monitoring system, consider raising your CPU limit or removing it entirely if the node has spare capacity.

For further details, consult the official Kubernetes documentation on Resource Management for Pods and Containers.
