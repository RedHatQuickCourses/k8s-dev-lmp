The Kubernetes scheduler, or kube-scheduler, is a controller that watches for new pods that have not yet been assigned to a node. Its core loop is straightforward: it takes a pod from the queue, identifies the best available node, and writes a binding object to the API server. Once that's done, the kubelet on the chosen node takes over to start the containers. Internally, the scheduler uses an informer to populate a priority queue. When new pods appear, an event handler pushes them onto the queue, and the scheduler processes them one by one.

Every pod goes through a three-phase scheduling cycle. First is Filtering, where the scheduler evaluates every node to see if it can host the pod. Nodes are eliminated if they lack sufficient resources, violate taints and tolerations, or fail node-affinity rules. If no node survives this stage, the scheduler moves to PostFilter to attempt preemption.

Second is Scoring. The remaining feasible nodes are ranked based on factors like resource balance, pod spreading, and affinity preferences. Each scoring plugin returns a value, which the framework totals to determine the final rank for each node.

Finally, there is the Binding phase. The scheduler assigns the pod to the highest-scoring node by creating a binding object in the API server. This process is asynchronous, which helps keep the main scheduling loop responsive and improves overall throughput.

The modern scheduler is built on the Scheduling Framework, a plugin architecture where every native feature is implemented as a plugin. This framework uses a series of extension points executed in a specific order. These include QueueSort, which sets the dequeueing order; PreFilter for initialization; Filter, which replaces older predicate functions; and PostFilter, which triggers preemption. Following these are PreScore and Score, which handle ranking. Then come Reserve, which optimistically claims resources; Permit, which can approve or deny the binding; and PreBind, which handles setup like volume provisioning. Finally, the Bind extension point writes the binding, and PostBind runs any necessary cleanup. Because native features use this same API, you can add custom logic without needing to fork the scheduler.

When the Filter stage finds no feasible node, the process moves to Preemption. The default implementation searches for a node where evicting lower-priority pods would make room for the new one. The algorithm works by removing pods with lower priority to check for feasibility, then carefully adding back as many as possible while keeping the new pod viable. The scheduler then selects the best candidate for eviction, deletes the victim pods, and re-queues the pending pod. Throughout this process, the scheduler uses a snapshot of the cluster state so that all plugins work with a consistent view.

You might notice that the scheduler intentionally sets its resync period to zero. Unlike many other controllers that periodically resync to catch missed events, the scheduler team prefers to expose and fix event-handling bugs directly, rather than masking them with a periodic full re-list.

It is important to remember that the kube-scheduler only acts at the time of pod creation; it never moves a running pod. To manage pods after they have started, you use complementary tools. The Descheduler evicts pods if their placement becomes suboptimal. The Horizontal Pod Autoscaler adjusts the number of replicas, while the Vertical Pod Autoscaler adjusts resource requests based on usage. Finally, the Cluster Autoscaler manages the underlying nodes themselves. Together, these tools provide the feedback loops necessary for a healthy, dynamic cluster.
