Persistence layer: etcd key-value store

Persistence Layer: The etcd Key-Value Store

In the Kubernetes architecture, the kube-apiserver acts as the gateway to the cluster, but the "source of truth" resides in etcd. Understanding how Kubernetes utilizes etcd is fundamental to grasping the distributed nature of the system.

Overview of etcd

etcd is a distributed, consistent, key-value store used to store all cluster data. It is not just a database for Kubernetes; it is the heartbeat of the control plane. When you interact with the Kubernetes API, you are modifying the state stored within etcd.

Key characteristics include: * Consistency: Based on the Raft consensus algorithm, ensuring that even in a distributed setup, all nodes agree on the state of the data. * Key-Value Structure: Kubernetes stores resources as serialized JSON or Protobuf objects, keyed by their path (e.g., /registry/pods/default/my-pod). * Watch Mechanism: etcd provides an efficient watch API that allows the kube-apiserver (and consequently, informers in controllers) to receive notifications when keys change, enabling the reactive, asynchronous nature of Kubernetes controllers.

How Kubernetes Uses etcd

When a user submits a manifest (a declarative configuration), the kube-apiserver performs the following steps: 1. Validation: Checks the request against schemas and webhooks. 2. Conversion: Converts the internal representation of the resource. 3. Storage: Writes the object into etcd.

Important Architectural Considerations

  • Vertical Scaling: It is critical to note that for the etcd and kube-apiserver control plane components, vertical scaling (adding more CPU/RAM to the existing nodes) is generally preferred over horizontal scaling. Expanding the etcd cluster size beyond 3 or 5 members often introduces latency due to the consensus overhead.

  • resourceVersion: Every object in etcd has a metadata.resourceVersion. This acts as a versioning mechanism for optimistic concurrency control. When a controller attempts an update, it must ensure its version matches the current version in etcd, preventing "lost updates" in a multi-writer environment.

Hands-on Activity: Observing etcd Keys

This activity requires an existing Kubernetes cluster where you have access to the etcd data directory or the etcdctl utility.

Prerequisites

  • Access to a Kubernetes control plane node.

  • etcdctl installed.

  • Environment variables set for etcd certs:

  • ETCDCTL_API=3

  • ETCDCTL_CACERT

  • ETCDCTL_CERT

  • ETCDCTL_KEY

Step 1: Querying the etcd store

To see how objects are stored, we will list the keys under the Kubernetes registry path.

# List all resources stored in the cluster registry
etcdctl get /registry --prefix --keys-only

Step 2: Inspecting a specific resource

Pick a pod name from your cluster and inspect its serialized representation.

# Replace <namespace> and <pod-name> with your values
etcdctl get /registry/pods/<namespace>/<pod-name> --print-value-only

Step 3: Observing the Change

  1. Open a new terminal and "watch" the registry:

etcdctl watch /registry/pods/<namespace>/<pod-name>

  1. In your primary terminal, update a label on that pod via kubectl.

  2. Observe the output in your etcdctl watch window. You will see the serialized JSON object being updated in real-time.

Troubleshooting Tips

  • Slow etcd Performance: Often caused by high disk I/O latency. Ensure etcd is backed by high-performance SSDs.

  • Compaction: etcd keeps a history of revisions. If the history grows too large, it consumes excessive memory. Kubernetes automatically performs compaction, but monitoring etcd_db_total_size_in_bytes is vital for cluster health.

  • Watch Cache: The kube-apiserver maintains a memory-resident "watch cache" to satisfy requests without hitting etcd directly for every read. If you see high latency on reads, verify the kube-apiserver cache metrics.
