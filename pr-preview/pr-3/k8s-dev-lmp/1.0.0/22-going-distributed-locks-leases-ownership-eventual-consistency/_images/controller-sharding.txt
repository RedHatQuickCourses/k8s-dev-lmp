In this module, we will explore controller sharding—a critical strategy for horizontal scaling in Kubernetes environments.

While leader election provides high availability by allowing a standby replica to take over if the active one fails, it doesn't solve the need for horizontal scaling. In a standard leader-elected setup, only one replica does the work at any given time. Controller sharding overcomes this limitation by distributing the reconciliation workload across multiple instances, with each instance responsible for a specific subset of resources.

When you manage thousands of resources with a single leader-elected controller, the reconciler inevitably becomes a bottleneck. Sharding divides this resource space so multiple replicas can work concurrently without conflict. This approach requires consistent resource assignment, reliable rebalancing when capacity changes, and careful management to ensure child resources remain aligned with their parent’s shard.

One effective implementation of this is label-based sharding. In this model, shard instances announce their availability via a Lease object. A sharder webhook then intercepts resource creation and update requests. This webhook uses consistent hashing to assign a shard label to each object, placing it on a virtual ring based on the object key and the available shards. Consequently, each controller instance only watches objects that carry its specific shard identity. Additionally, owned objects—those with owner references—automatically inherit the shard assignment of their parent.

Managing shard capacity requires a coordinated process. When scaling down by removing a shard, the instance releases its Lease, and the sharder marks it as dead. Orphaned objects then have their labels cleared so the webhook can reassign them to remaining shards during the next update.

Conversely, when scaling up by adding a shard, the new instance acquires a Lease and is marked ready. The sharder then identifies objects that should transition to the new shard and applies a drain label. The current shard stops reconciling those objects, removes the labels, and the webhook successfully reassigns them to the new shard. This coordinated handoff ensures that no two shards attempt to reconcile the same object simultaneously.

Let’s look at a real-world example: OpenShift Ingress Controller Sharding. OpenShift supports running multiple ingress controllers, where each is responsible for a subset of routes. You can configure this sharding using the routeSelector and namespaceSelector fields within the IngressController resource.

OpenShift supports two primary models. First is the traditional, non-overlapping model, where each route is served by exactly one controller using mutually exclusive selectors. The second is the overlapped model, where routes can match multiple controllers. While this allows for complex routing topologies, it requires very careful planning.

Common use cases for ingress sharding include separating internal from external traffic, isolating workloads with different reliability requirements, balancing loads across multiple router instances, and implementing blue-green deployment strategies.

It is important to remember that each Ingress Controller requires its own unique DNS entry. Keep in mind that routers do not forward unknown routes to other routers. If a route does not match any selector, it will be unreachable.

Finally, when multiple ingress controllers serve the same route in overlapped mode, each controller writes its own entry into the status dot ingress array. This is handled using atomic list types, which prevents concurrent writers from corrupting each other’s status entries.
