In this module, we will explore Security Context and hardening within Kubernetes. A Security Context is the primary mechanism for hardening workloads at the pod specification level, as it defines privilege and access control settings for your pods and containers.

Kubernetes supports these settings at two different scopes. First, there is the pod-level security context, defined under `spec.securityContext`. Settings applied here affect every container within the pod, including group and user identifiers. Second, there is the container-level security context, defined under `spec.containers[].securityContext`. This level is used for container-specific settings like privilege escalation, file system permissions, and system call filtering. If a field is defined at both levels, the container-level setting will always take precedence.

There are several key fields you should be familiar with when configuring a security context. These include `runAsUser` and `runAsGroup` to set the identity of processes, and `runAsNonRoot` which rejects a pod at admission if it attempts to run as root. You can also use `readOnlyRootFilesystem` to prevent writes outside of mounted volumes, and `allowPrivilegeEscalation` to restrict child processes. Finally, you can use `capabilities` to add or drop specific Linux privileges, and `seccompProfile` to filter which system calls a process can make.

By setting `runAsNonRoot` to true, forcing a specific user ID, and using the `RuntimeDefault` seccomp profile, we ensure a secure foundation. Within the container spec, we disable privilege escalation, drop all Linux capabilities, and mount the root filesystem as read-only. This configuration is compatible with most workloads while significantly reducing the attack surface.

Beyond manual configuration, managing security profiles across a cluster can be challenging. The Security Profiles Operator, or SPO, is a Kubernetes project that automates the lifecycle management of seccomp, SELinux, and AppArmor profiles. It uses custom resource definitions for each profile type. Two features make the SPO particularly powerful: first, it can record workload behavior to automatically generate a least-privilege profile; and second, it can use profile binding to automatically link security profiles to specific container images upon deployment.

If you are working with OpenShift, you will encounter Security Context Constraints, or SCCs. These are cluster-scoped policies that define exactly what security contexts a pod is allowed to use. When you create a pod, the OpenShift admission controller evaluates the pod's service account against these constraints. If the requested settings violate the applicable SCC, the pod is rejected. 

OpenShift provides several default constraints. The `restricted-v2` SCC is the default for most workloads, enforcing the use of non-root users and requiring seccomp profiles. The `anyuid` constraint allows running as any user ID, which is sometimes necessary for legacy applications. Finally, the `privileged` SCC provides unrestricted access to the host.

A very important caution: granting the `privileged` SCC to a workload effectively disables all pod-level security controls. You should only use this for infrastructure components that genuinely require host-level access, and you should always assign it through a dedicated service account.

For further reading, please consult the official Kubernetes documentation on configuring security contexts and visit the GitHub repository for the Security Profiles Operator.
