Let’s begin by exploring the client-go architecture.

Client-go is the official Go client library for the Kubernetes API server. It provides the essential event-driven programming primitives that every Kubernetes controller and operator is built upon. In fact, even the command-line tool, kubectl, uses client-go under the hood. If you are planning to build your own Kubernetes controller, mastering this library is a foundational requirement.

Conceptually, there are three layers that sit between you, the developer, and the API server. First, at the bottom, is the API server itself, which acts as the source of truth for cluster state. Second is client-go, which provides the typed clients, informers, listers, caches, and workqueues. Third is controller-runtime, a higher-level framework that simplifies development by masking many of the complex details of client-go’s event-oriented architecture.

Within client-go, you will primarily work with four key packages: the tools/cache package, which contains informers and indexers; the kubernetes package, which provides typed clientsets; the dynamic package for untyped clients; and the discovery package for API group discovery.

Every controller based on client-go relies on a set of core components found within the tools/cache package. Let's look at those individually.

First is the Reflector. The Reflector is responsible for mirroring the API server’s state into a local store using a process called List and Watch. When it starts, it performs an initial list operation to fetch all existing objects, recording the resource version. It then opens a long-running watch connection starting from that version to receive incremental updates. When a change is detected, the Reflector places the object, along with the change type, into a DeltaFIFO queue.

This brings us to the DeltaFIFO. This is a producer-consumer queue that stores resource events as incremental deltas. The Reflector acts as the producer, while the Informer’s process loop acts as the consumer. DeltaFIFO is critical for controller correctness because it guarantees exactly-once, in-order processing for each resource. It also performs deduplication; if multiple updates arrive for the same object key before the consumer processes them, the queue coalesces them so that the controller only sees the latest state.

Next is the Indexer. The Indexer is a thread-safe local cache that stores objects popped from the DeltaFIFO. It uses a default function to generate keys in a namespace-slash-name format. 

I must share an important warning here: multiple controllers within the same process share the Indexer cache. Because of this, you must never mutate a cached object—even something as simple as updating an annotation—without creating a deep copy first. Doing so will corrupt the object for every other controller that reads it. Always use the generated DeepCopy method before modifying any cached object. 

Also, keep in mind that each resource stored in etcd has a hard size limit of approximately one-and-a-half megabytes, so be mindful of this when designing custom resources with large specifications or status fields.

Finally, we have the SharedInformerFactory. This component multiplexes watchers across controllers, ensuring that only one API server connection is maintained per resource type within a process. This is a significant optimization that saves API connections and reduces serialization costs and server-side memory usage. The SharedInformer interface provides the contract for these informers, allowing you to register event handlers and start the synchronization process.

To visualize how this works, think of the data flow as a pipeline. Data starts at the API server and is retrieved by the Reflector. It moves into the DeltaFIFO, then into the Informer’s Indexer or cache. From there, it triggers your registered event handlers, which enqueue keys into your workqueue. Finally, your controller’s sync handler picks up those keys to perform the actual reconciliation logic. 

As a controller author, you focus on the bottom half of this pipeline—specifically the event handlers, the workqueue, and the sync handler—while client-go manages the heavy lifting of the top half.

For further study, you can consult the official client-go tools/cache documentation, the sample-controller guide, or the various presentations available on Kubernetes informers. These resources will provide deeper technical context as you begin building your own controllers.
