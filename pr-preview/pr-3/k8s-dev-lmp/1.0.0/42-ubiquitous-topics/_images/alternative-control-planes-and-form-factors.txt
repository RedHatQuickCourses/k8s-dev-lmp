In a standard Kubernetes cluster, the control plane—consisting of the API server, etcd, the controller manager, and the scheduler—runs alongside your workload nodes. This model works well for general-purpose environments, but as Kubernetes expands into multi-tenant platforms, edge computing, and resource-constrained devices, we often see alternative architectures that trade off management overhead, resource footprint, and provisioning speed to better suit specific needs.

Let’s explore some of these alternatives, starting with HyperShift.

HyperShift implements hosted control planes. In this model, the control plane for each tenant cluster runs as a set of pods inside a central management cluster, while the tenant's worker nodes form a separate workload cluster that connects over the network. The management cluster treats each hosted control plane like any other workload. Key benefits include faster provisioning, where clusters can be ready in seconds; reduced per-cluster overhead by sharing control-plane nodes; and centralized management for upgrades and patches. HyperShift is the foundation for Red Hat OpenShift’s hosted offerings, such as ROSA.

Next, we have kcp. Unlike a standard distribution, kcp is a Kubernetes-like control plane that serves as a generic API platform without scheduling workloads. It provides the core Kubernetes API machinery but has no concept of nodes or pods. It introduces several powerful concepts, including workspaces for lightweight, isolated API scopes; transparent multi-cluster scheduling via a syncer agent; and API export and binding, which allows platform teams to publish reusable APIs for application teams. Essentially, kcp separates the "what"—the API resources—from the "where"—the physical clusters running the workloads.

Now, let's look at MicroShift, which is a minimal Kubernetes distribution from Red Hat designed for resource-constrained environments. It packages the control plane components into a single binary that runs as a systemd service. It features a minimal footprint, targeting devices with as little as two CPU cores and two gigabytes of RAM. It also provides OpenShift API compatibility, standalone operation for disconnected environments, and integrated networking using OVN-Kubernetes. This is an ideal choice for industrial IoT gateways and automotive platforms.

Another popular choice is k3s, a lightweight, CNCF-certified distribution maintained by SUSE. It bundles all control-plane components and the kubelet into a single, compact binary of about 70 megabytes. By using SQLite as the default datastore, removing legacy cloud-provider plugins, and offering first-class support for ARM hardware, k3s is highly efficient. It also comes "batteries included" with tools like Traefik for ingress and CoreDNS, making it a great fit for edge computing, developer workstations, and CI/CD environments.

To summarize how these architectures compare, consider their primary differences: 
While a standard Kubernetes setup uses self-hosted control planes on dedicated nodes and requires a multi-node etcd quorum, HyperShift hosts control planes as pods. Meanwhile, MicroShift and k3s utilize a single binary architecture to minimize their footprint, with MicroShift using an embedded etcd and k3s defaulting to SQLite. Your choice depends on your target environment, whether you are managing multi-tenant platforms at scale, or if you are deploying to constrained edge hardware.

It is important to remember that these architectures are not mutually exclusive. A platform team might run HyperShift in a data center to manage hundreds of tenant clusters, while simultaneously deploying MicroShift or k3s on edge devices. The ultimate decision depends on where you need your control plane to live, the number of clusters you are managing, and the resources available at each location.
