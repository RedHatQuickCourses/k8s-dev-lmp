The Kubernetes scheduler is a specialized controller designed to watch for pods that have not yet been assigned to a node. Its primary job is to take those pods and place them on the most appropriate node available. The scheduler’s core loop is remarkably straightforward: it pulls a pod from a queue, identifies the best-suited node, and writes a binding object back to the API server. Once that binding is complete, the Kubelet on the target node takes over to begin running the containers.

Internally, the scheduler uses an informer to maintain a priority queue of unscheduled pods. When a new pod is created, an event handler pushes it onto this queue. The scheduler then processes these pods one by one, running them through a complete scheduling cycle.

During the scheduling cycle, every pod passes through three distinct phases. First is the filtering phase, also known as predicates. Here, the scheduler evaluates every node to see if it is capable of running the pod. Any node that lacks sufficient CPU, violates taints and tolerations, or fails node-affinity rules is immediately eliminated. If no node survives this filtering process, the scheduler moves to the post-filter stage to attempt preemption.

Second is the scoring phase, or priorities. Once the list of feasible nodes is narrowed down, the scheduler ranks them. This process considers factors like balanced resource utilization, pod spreading across zones, and inter-pod affinity preferences. Each scoring plugin returns a value, and the framework calculates a sum to determine a final rank for every node.

Finally, there is the binding phase. The scheduler assigns the pod to the highest-scoring node by creating a binding object in the API server. Importantly, this binding runs asynchronously, which ensures the main scheduling loop isn't blocked and maintains high throughput.

The modern scheduler is built on the Scheduling Framework, a plugin architecture where all built-in features—such as resource checks or affinity rules—are implemented as plugins. The framework processes these through several extension points in a specific order. 

These include QueueSort, which orders the pods; PreFilter, which initializes plugin state; Filter, which checks node feasibility; and PostFilter, which handles cases where no node passes. After filtering, the process continues with PreScore, which prepares state; Score, which ranks the nodes; and Reserve, which claims resources. Finally, the process reaches Permit, which can gate the binding, followed by PreBind for setup tasks like volume provisioning, the actual Bind operation, and PostBind for final cleanup or notifications. Because all features use this same plugin API, you can introduce custom logic without needing to modify the scheduler itself.

When the filtering stage finds no feasible node, the scheduler triggers the post-filter extension point, which initiates preemption. The default preemption logic looks for a node where evicting lower-priority pods would create enough room for the pending pod. The scheduler evaluates potential victims based on priority, attempts to preserve those protected by Pod Disruption Budgets, and selects the candidate that results in the least amount of disruption and churn. Once victims are terminated, the pending pod is re-queued for scheduling.

You might notice that the scheduler does not use periodic resyncs, unlike many other Kubernetes controllers. This is an intentional design choice. The maintainers prefer to address event-handling bugs directly rather than masking them with periodic re-lists, ensuring higher reliability in the long term.

Finally, keep in mind that the kube-scheduler only acts at the time of pod creation; it does not move pods that are already running. To manage the cluster lifecycle, you will often use complementary tools. The Descheduler can evict pods that are placed suboptimally, while the Horizontal and Vertical Pod Autoscalers manage pod scaling and resource requests. Additionally, the Cluster Autoscaler can provision or remove nodes as needed. Together, these tools provide a complete feedback loop for your cluster.
