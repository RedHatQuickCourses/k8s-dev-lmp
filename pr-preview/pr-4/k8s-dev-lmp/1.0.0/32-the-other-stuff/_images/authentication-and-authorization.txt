Every request to the Kubernetes API server undergoes a two-step process: first authentication, and then authorization, before reaching admission control and storage. Understanding these layers is essential for building controllers and operators that interact with the API safely. For a deeper look at the complete process, you can refer to the API Request Lifecycle documentation.

Let’s begin by looking at authentication, which is the process of verifying who you are. 

In Kubernetes, identity falls into two categories. First, there are Service accounts, which are managed by the Kubernetes API. These are bound to namespaces and backed by Secrets or projected token volumes. Importantly, every pod automatically receives a service account token mounted at the path `/var/run/secrets/kubernetes.io/serviceaccount/token`.

The second category is normal users. It is important to note that Kubernetes does not have a native `User` object. Instead, identity is derived entirely from the authentication layer through a valid client certificate, a bearer token, or an OIDC token.

The API server evaluates authentication plugins in a specific order. The first plugin that succeeds stops the process and populates a user information structure with the username, UID, groups, and any additional fields. Supported methods include X.509 client certificates, bearer tokens used for cluster setup, OIDC tokens for human users, service account tokens, and webhook token reviews for external authentication services. If a request does not match any authenticator, it is treated as anonymous, assigned to the `system:anonymous` user and the `system:unauthenticated` group.

Once a request is authenticated, we move to authorization, which determines what the user is allowed to do.

The API server consults a chain of authorizer modules. Each module returns one of three responses: Allow, Deny, or No Opinion. An "Allow" or "Deny" decision stops the chain, while "No Opinion" passes the request to the next module.

The most common authorizer is Role-Based Access Control, or RBAC. This system uses `Role` and `ClusterRole` objects to define allowed actions on API resources, while `RoleBinding` and `ClusterRoleBinding` map those roles to users, groups, or service accounts. Keep in mind that RBAC is purely additive; it only grants permissions and never explicitly denies them.

Next, we have the Node authorizer, which is designed specifically for kubelets. A kubelet authenticates as a node, and this authorizer limits its access to only the resources, such as pods, secrets, and config maps, that are specifically bound to that node. This graph-based decision prevents a compromised node from accessing secrets belonging to pods on other nodes. If a request falls outside this specific graph, the Node authorizer returns "No Opinion," passing the request along to RBAC. Additionally, the `NodeRestriction` admission controller provides further limits on what properties a kubelet can modify.

A useful tip to remember is that the `kubectl auth can-i --list` command only displays RBAC-granted permissions. If you have rights granted by the Node authorizer, they will not appear in this output, which can be misleading during security audits.

For more complex requirements, Kubernetes supports webhook authorization. This allows you to send a `SubjectAccessReview` to an external service, which can return an explicit "Deny" rule that standard RBAC cannot express.

Finally, there is an emerging approach called ReBAC, or Relation-Based Access Control, inspired by Google’s Zanzibar research. Instead of flat role mappings, it models authorization as a graph with typed nodes and directed relations. 

There are several advantages to this model. First, it supports native deny rules. Second, it allows for inheritance, where granting access to a parent object automatically propagates that access to child resources. Third, it enables cross-system integration, allowing external permission sources like LDAP groups or cloud IAM roles to be projected into the same graph as your Kubernetes objects. While ReBAC is still experimental, it represents the future direction for fine-grained, graph-aware authorization in the Kubernetes ecosystem.
