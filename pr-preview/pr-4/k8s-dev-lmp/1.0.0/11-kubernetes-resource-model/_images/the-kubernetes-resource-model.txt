Welcome to this overview of the Kubernetes Resource Model. 

To understand Kubernetes, we must first recognize that it is not merely API-driven; it is fundamentally API-centric. At the core of the control plane sits the API server, or apiserver. This component implements the common functionality for every system API. Whether you are a user client or a controller implementing business logic, everyone interacts through these same APIs. Meanwhile, all persistent cluster state is maintained within etcd.

This architecture intentionally blurs the line between built-in system components and those built on top of it. Through extension mechanisms like Custom Resource Definitions and aggregated API servers, you can expand the number of resource types without modifying the core Kubernetes code. This approach ensures that any API using these standard patterns immediately integrates with existing tools and libraries.

Kubernetes relies on declarative control. This means user intent is recorded as a desired state within API resources. Asynchronous controllers then work to make the observed state match that desired state. These controllers do not talk to etcd directly, nor do they use private internal APIs. Instead, they use the Kubernetes API as a shared coordination point. 

These controllers are designed to be level-based rather than edge-based. This means a controller can function correctly by comparing the current observed state with the desired state, even if it missed some intermediate updates. This design significantly increases fault tolerance. However, controllers can also achieve the efficiency of edge-triggered systems by using the watch API to stay updated on changes in real-time.

The resource model is built on several key properties that ensure resilience and extensibility. First, there are no hidden internal APIs; all are visible and available based on authorization policies. Second, Kubernetes avoids atomic cross-resource transactions. Updates to the desired state are immediate, but actuation is asynchronous and eventual. Third, there are no exclusive owners for resources; multiple parties can read and write to them, meaning controllers must constantly verify their assumptions. Fourth, status is always reconstructable by observation, avoiding the need for opaque internal persistent state. Finally, object references use predictable, immutable names rather than URLs, which facilitates loose coupling and easier recovery.

When looking at the API topology, you will notice a consistent URL structure that includes the group, version, namespace, resource type, and name. Resources are grouped into related types that evolve together across versions and are scoped by user-created namespaces. 

Every resource includes metadata, such as labels for filtering and grouping, and annotations for configuration or checkpointing. Most resources are split into a spec, representing the desired state, and a status, representing the observed state. The status subresource allows for distinct authorization policies for users and controllers. 

When you define a resource, such as a Pod, you will typically see the API version and the kind of resource defined at the top. The metadata section holds identifying information, while the spec section details the container configuration, such as images, ports, and arguments.

Each resource lifecycle follows a strict sequence of behaviors. When a mutation occurs, the system performs authentication and authorization, applies defaults, converts versions, runs admission control, and validates the fields. It also ensures idempotence through immutable names and uses optimistic concurrency to prevent conflicts, while recording all changes in audit logs.

Deletion also follows specific patterns, such as graceful termination, the use of finalizers to block deletion until external cleanup is finished, and garbage collection, where resources are automatically removed once their owners are gone. For read operations, the system supports listing resources, filtering via label selection, and watching for changes.
